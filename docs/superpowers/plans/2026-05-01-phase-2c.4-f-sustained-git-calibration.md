# Phase 2C.4 / F — Sustained git calibration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the 2C.2 baseline pipeline once with two scenario-file modifications (instrumentation thresholds + iteration bumps) so observed p99 evidence is available for `git.clone@v1`, `git.diff@v1`, `git.commit@v1`, and per-tree-split `git.status@v1`. Update `ops/slo/git.yaml` from PROVISIONAL/ROUGH/SMOKE to CALIBRATED (or honest lower tier) per the 2C.2 calibration heuristic. Ship `v0.7.0`.

**Architecture:** Two PR-bundles + one operational closure step. B1 ships code-only changes (scenario thresholds + iteration bumps) — committable immediately, CI green. B2 is operator-driven: an operator runs `make load-baseline` locally (~50 min), analyzes the auto-generated calibration report, derives new `le` values from observed p99 using the 2C.2 heuristic (smallest existing bucket ≥ 3× p99 with documented headroom), updates `ops/slo/git.yaml`, regenerates Sloth rules, and commits everything (report + evidence + YAML + CHANGELOG) in a single PR. Closure tags v0.7.0 on B2's merge commit and marks the roadmap closed.

**Tech Stack:** k6 0.58.0 (load harness), pinned compose envelope (2 CPU / 2 GiB runtime per ADR 0008), Sloth 0.16.0 (SLO render), Prometheus + promtool (validation), `generate-report.sh` (existing 2C.2 Markdown generator). NO Go code changes. NO new dependencies.

### Task 2.5: Derive new `le` values per the 2C.2 heuristic

**Files:** none — this is analysis. The YAML edits happen in Task 2.6.

- [ ] **Step 1: Apply the heuristic to each capability**

For each git capability with `CALIBRATED`-tier eligibility (sample count ≥ 100 or ≥ 30 for the bumped scenarios):

1. **Compute `target_le`** = the smallest bucket from `{0.1, 0.25, 0.5, 1, 2, 3, 5, 10, 30, 60}` such that `target_le >= 3 * observed_p99`.
2. **Compute `headroom`** = `target_le / observed_p99`. Aim for 3-5×; document the actual value.
3. **Decision tier** per spec §3 P6 + §6:
   - `CALIBRATED` (high confidence): N ≥ 100 (or ≥ 30 for the scenarios that ran fewer iterations), p99 stable, headroom ≥ 3×.
   - `SMOKE_CALIBRATED` (limited): N 30-100, OR p99 unstable.
   - `ROUGH_NO_CHANGE`: N < 30 OR variance too high — keep PROVISIONAL.

**Worked example (HYPOTHETICAL — not the actual answer):**

If the report shows `git.clone@v1 p99 = 1.2s` with N=60 samples and stable distribution:
- `target_le = 5` (5s, smallest bucket ≥ 3 × 1.2 = 3.6s; the next-smaller bucket 3 is < 3.6).
- `headroom = 5 / 1.2 = 4.17×` (within 3-5× target).
- Decision: `CALIBRATED` (N=60 ≥ 30 with bumped iterations + stable p99 + headroom 4.17×).
- New YAML: `le="5"` (was `"30"`).
- Justification: "5.0× headroom over measured p99 (1.2s); existing bucket 5s already in `obs.DurationBuckets`; no histogram boundary additions; existing baseline data remains valid."

Apply the same process to git.diff, git.commit. For git.status, additionally consider the per-tree split: if `dirty-tree p99 > 1.5 × small-repo p99`, base the threshold on dirty-tree's p99 (worst case); otherwise use the aggregated p99.
