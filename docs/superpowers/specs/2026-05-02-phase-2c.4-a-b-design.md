## 1. Summary

Sub-project A+B replaces the `null-receiver` placeholders in
`ops/alertmanager/alertmanager.yaml` (added in Phase 2C.1) with **real
alert receivers**: PagerDuty (Events API v2) for `severity=critical`,
Slack `#incidents` for critical visibility, Slack `#ops` + a Linear
webhook adapter for `severity=warning`. `severity=info` remains
silenced at the routing root.

Because Alertmanager has **no native receiver for Linear**, A+B also
ships a small Go service (`linear-webhook-adapter`) at
`cmd/linear-webhook-adapter/` that translates Alertmanager webhook
payloads into Linear GraphQL `IssueCreate`/`IssueUpdate`/`IssueArchive`
mutations, with deduplication via a deterministic label hash derived
from Alertmanager's `groupKey`. The adapter is a separate binary,
separate container, separate port (9095), in the same Go module —
deliberately decoupled from the runtime-adapters execution path.

A+B also delivers an end-to-end smoke target (`make smoke-receivers`)
that exercises all 3 receivers + the silenced info path against the
test tenant, plus a 4-layer CI guardrail to prevent production
credentials from ever reaching CI.

The routing tree shape, group_by, inhibit rules, and timing from 2C.1
are **unchanged** — A+B only swaps receivers and adds the Linear
adapter as a new service. Six routing tests in
`ops/alertmanager/alertmanager_routing_test.go` are updated to match
the new receiver names but keep their original invariants.

## 2. Goals / non-goals

### Goals

- Replace `null-receiver` in `severity=critical` route with a receiver
  that pages a real on-call rotation via PagerDuty Events API v2 and
  posts visibility to Slack `#incidents`.
- Replace `null-receiver` in `severity=warning` route with a receiver
  that posts to Slack `#ops` AND opens/updates/closes Linear issues
  via a webhook adapter.
- Keep `severity=info` silenced at the routing root (invariant I-AB.1).
- Ship a Linear webhook adapter as a separate Go binary + container
  in the same Go module, hexagonal layout, stateless, no local
  persistence.
- Ship `make smoke-receivers` that exercises all 3 receivers +
  silenced info path end-to-end against the test tenant, with
  programmatic verification per receiver (no "look at Slack manually").
- Ship 4-layer CI guardrail: gitleaks secret scanning, env var name
  guard, bootstrap-time mode lock, per-receiver tenant fingerprinting.
- Ship test tenant setup documentation
  (`docs/test-tenant.md`) with reproducible steps.
- Ship code that runs identically against test tenant or production
  tenant — the only difference is which env vars are loaded
  (test-tenant-ready for `v0.8.0`; production adoption is an
  operational milestone, not a code change).

### Non-goals

- Re-designing the Alertmanager routing tree. The tree from 2C.1
  (3 routes, group_by alertname+adapter+capability, severity-tiered
  timings, inhibit rules) is unchanged. The 2C.1 file header
  declares: *"Track 2C.4 will swap receivers for real integrations
  without changing the tree."*
- Adding new alert rules or modifying existing alert objectives. F
  delivered the calibrated targets; A+B only changes how those
  alerts are delivered, not what they alert on.
- Production tenant procurement (PagerDuty paid plan, Linear paid
  plan, etc.). v0.8.0 ships test-tenant-ready; prod adoption is
  follow-up operational work that does NOT require code changes.
- Multi-region / failover for the webhook adapter. Adapter is a
  single instance per environment; if Linear is unreachable, the
  adapter returns 5xx and Alertmanager retries. Acceptable
  degradation.
- Custom severity tiers beyond critical/warning/info. The taxonomy
  is locked since 2C.1.
- CI integration of the smoke target as a gate. Smoke is operator-
  driven for v0.8.0; CI integration is deferred.
- Slack bot for two-way interaction (ack alerts from Slack, etc.).
  Bot scope is read-only (`channels:history`) for smoke verification.

## 3. Closed decisions

The following decisions were closed during the 2026-05-02 brainstorming
session and do NOT reopen during implementation without an explicit
ADR.

### D2C4AB.1 — Routing tree from 2C.1 stays unchanged

The 3-route shape (critical / warning / info), `group_by:
[alertname, adapter, capability]`, timing per severity (critical
30s/5m/30m, warning 1m/15m/4h), inhibit rule (critical-fast-burn
inhibits warning-slow-burn per `{sloth_slo, capability}`), and
`severity=info` falls-through to root null-receiver — all unchanged
from 2C.1.

### D2C4AB.2 — `ops-critical` receiver = pagerduty + slack #incidents

Critical alerts route to a single receiver `ops-critical` with TWO
backends:

- `pagerduty_configs:` — pages on-call via PagerDuty Events API v2
- `slack_configs:` — posts to `#incidents` for team visibility

Both fire in parallel. Industry-standard pattern: pager wakes the
on-call, chat surface gives the rest of the team context.

### D2C4AB.3 — `ops-warnings` receiver = single receiver, multi-config (Option A)

Warning alerts route to a single receiver `ops-warnings` with TWO
backends:

- `slack_configs:` — posts to `#ops`
- `webhook_configs:` — POSTs to the Linear webhook adapter at
  `http://linear-webhook:9095/webhook`

Rejected alternatives:

- **Option B** (sub-routes with `continue: true`): would break
  `TestAlertmanager_SubRoutesDoNotContinue` and reopen a 2C.1
  decision.
- **Option C** (cascaded — Slack receiver invokes Linear): couples
  the two backends; failure of one cascades to the other.

Option A keeps backends independently retryable at the Alertmanager
notification dispatcher level.

### D2C4AB.4 — Linear adapter is a separate binary, separate container

Linear webhook adapter is NOT mounted on the runtime-adapters HTTP
server. It is a separate binary at `cmd/linear-webhook-adapter/`,
built as a separate Docker image (multi-stage `--target
linear-webhook-adapter`), deployed as its own container in
`ops/local/compose.yaml`, listening on port `9095`. Same Go module
as runtime-adapters (shared logging, OTel setup, errors package).

Rationale:

- D1.1 / D1.2 (CLAUDE.md): runtime-adapters is the boundary between
  decision and execution; mixing alert tracking into the same process
  violates the boundary.
- I-AB.4 (stateless): process boundary enforces statelessness
  naturally; restart mid-incident does NOT change behavior.
- Blast radius: a goroutine leak in Linear API client retry storm
  must NOT kill runtime-adapters which is processing executions.
- HTTP listener concerns: orchestrator-bound traffic to runtime
  has different access control and authorization than
  alertmanager-bound webhook traffic.

### D2C4AB.5 — Adapter follows hexagonal layout

```
cmd/linear-webhook-adapter/main.go        — entry point
internal/integrations/linear/
    domain/                                — types (Issue, Severity, Dedup)
    application/                           — webhook handler, dedup logic, lifecycle
    ports/                                 — LinearAPIClient interface
    infrastructure/                        — LinearGraphQLClient concrete impl
```

Mirrors the existing repo's hexagonal pattern. Tests at each layer
(unit + integration via testcontainers + mock Linear endpoint).

### D2C4AB.6 — Multi-stage Dockerfile with target

Single `Dockerfile` at repo root with multiple stages:

- `runtime-adapters` stage builds `cmd/runtime-adapters` (existing)
- `linear-webhook-adapter` stage builds
  `cmd/linear-webhook-adapter` (new)

CI / compose use `docker build --target <name>` to select. Avoids
maintaining two parallel Dockerfiles.

### D2C4AB.7 — Dedup strategy: hash-derived label

Label format: `alert:` + first 12 chars of `hex(sha256(groupKey))`.

- 12 chars provides collision probability `1 / 16^12` ≈ `3.5e-15` —
  negligible for our volume of distinct alert groupings (~250 max
  per the cardinality bound: ~25 SLO rules × ~10 capability
  combinations).
- Label-safe (no special chars).
- Linear-API-queryable via `issues(filter: { labels: { name: {
  eq: "alert:abc123def456" } } })`.

Adapter also applies a constant label `alert-managed` to every issue
it creates, so humans can filter all adapter-managed issues in
Linear UI.

Rejected alternatives: title-strict matching (humans rename
titles), title+label (more complex, queries slower), body marker
(full-text search slow + humans edit body).

### D2C4AB.8 — Issue lifecycle

| Webhook event | Adapter action |
|---|---|
| `status: firing`, no existing issue | Create new issue with full schema (§7.4) |
| `status: firing`, existing issue (matched by `alert:<hash>` label) | Update most recent — refresh body, optionally add comment (anti-spam D2C4AB.9) |
| `status: resolved`, existing open issue | Close issue (state → "Cancelled") + final comment with timestamp + duration |
| `status: resolved`, no existing issue | Log warning + return 200 OK (race-condition safe; do NOT trigger Alertmanager retry) |

### D2C4AB.9 — Re-firing anti-spam

On re-firing for an existing issue, the adapter adds a comment
ONLY if at least one of the following is true:

- The set of alerts in the group has changed (new fingerprints
  arrived or old ones dropped).
- The severity or status flipped.
- A configurable minimum interval has elapsed since the last
  comment (default: 15 minutes; env var
  `LINEAR_RECOMMENT_MIN_INTERVAL`).

Otherwise the adapter only refreshes the issue body's `Last update`
timestamp and `Active alerts in group` count. Prevents Linear
ticket spam during alert flapping.

### D2C4AB.10 — Priority mapping

| Alertmanager severity | Linear Priority |
|---|---|
| `critical` | P1 (Urgent) |
| `warning` | P3 (Medium) |
| `info` | n/a (silenced before reaching adapter) |

Warnings stay at P3 (not P2) by default; promote individual alerts
to P2 via Alertmanager labels if needed (out of scope for v0.8.0).

### D2C4AB.11 — Smoke injection via `amtool alert add`

The smoke target uses `amtool alert add` (the standard Alertmanager
CLI, already used in `make test-alertmanager`) to inject synthetic
alerts. Tests the actual routing tree, not bypassed receiver
endpoints.

Rejected alternatives: modifying Prometheus rules and waiting for
firing (slow, alters running stack), curl-direct-to-Alertmanager-API
(equivalent but verbose), curl-direct-to-receivers (skips routing,
defeats the smoke).

### D2C4AB.12 — Per-receiver smoke verification

| Receiver | Verification method | Requires |
|---|---|---|
| PagerDuty | API query: `GET /incidents?service_ids[]=...&statuses[]=triggered` filtered by alert title | `PAGERDUTY_TEST_API_TOKEN` + `PAGERDUTY_TEST_SERVICE_ID` |
| Slack `#incidents` / `#ops` | API query: `GET conversations.history` filtered by message text | Slack bot user with `channels:history` scope; channel IDs in env |
| Linear | API query: `issues(filter: { labels: { name: { eq: "alert:<hash>" } } })` | `LINEAR_TEST_API_TOKEN` + `LINEAR_TEST_TEAM_ID` |

Slack requires a bot user in the test workspace with read-only
`channels:history` scope on the sandbox channels. This is in addition
to the incoming webhook used for Alertmanager → Slack delivery.
Documented in §11.

Rejected alternatives: trust + log inspection (does NOT verify the
message rendered correctly); webhook proxy capturer (bypasses real
Slack — does NOT verify Slack accepts the payload).

### D2C4AB.13 — Smoke includes negative test for `severity=info`

Smoke MUST also inject a `severity=info` alert and verify that
**none of the 4 receivers** received it. Sin esto, una regresión que
hace que info se filtre pasaría el smoke en silencio.

### D2C4AB.14 — Smoke auto-cleanup with fail-safe

Cleanup runs after verification:

1. PagerDuty: `PUT /incidents/{id}` → status=resolved + final note.
2. Slack: `chat.delete` on the test messages (requires bot scope
   `chat:write`).
3. Linear: archive the test issues (state → Cancelled, optional
   `IssueArchive` mutation).
4. Alertmanager: `amtool silence add` for the SmokeTest* alertnames
   (5min) to prevent re-fire during cleanup races.

If any individual cleanup step fails: log warning + continue with
the remaining steps. Cleanup is housekeeping, not part of the
PASS/FAIL contract; verification (§D2C4AB.12) determines success.

### D2C4AB.15 — Smoke as Bash script + Make wrapper, operator-driven

`ops/smoke/smoke-receivers.sh` (Bash) wrapped by Make target
`smoke-receivers`. Same pattern as `ops/load/lib/generate-report.sh`,
`verify-limits.sh`. NOT a CI gate for v0.8.0 (matches the
operator-driven pattern of `make load-baseline`); CI integration is
deferred follow-up.

### D2C4AB.16 — 4-layer CI guardrail

| Layer | Mechanism | Catches |
|---|---|---|
| 1 — Secret scan | gitleaks GH Action on every PR + push | Accidental credential commits |
| 2 — Env var name guard | CI workflow job rejects any `*_PROD_*` env var | Scope expansion of GitHub Secrets |
| 3 — Bootstrap mode lock | Both runtime-adapters and linear-webhook-adapter abort startup if `CI=true && RUNTIME_TENANT != test` | CI runs against prod tenant |
| 4 — Tenant fingerprinting | Both bootstraps log + assert tenant identifiers (PagerDuty service_id, Linear team_id, Slack workspace prefix) match test tenant config | Bypass of layer 3 |

Convention: production credentials env vars use prefix or infix
`PROD_` (e.g., `PAGERDUTY_PROD_ROUTING_KEY`,
`LINEAR_PROD_API_TOKEN`); test tenant vars omit `PROD_`.

### D2C4AB.17 — Three-bundle plan

- **B1**: Alertmanager wiring with native receivers (PagerDuty +
  Slack only — no Linear yet).
- **B2**: Linear webhook adapter as new service + Layers 1+2+4 of
  CI guardrails + Layer 3 for the adapter side.
- **B3**: Smoke target + Layer 3 for runtime-adapters side + test
  tenant docs + CHANGELOG 0.8.0.

Each bundle merges independently with CI green; each closes value
on its own.

### D2C4AB.18 — v0.8.0 ships test-tenant-ready

Code is functionally complete in v0.8.0. Production adoption is a
purely operational milestone (which env vars are set in prod
deployment) — does NOT require code changes. This decouples
`v0.8.0` release from prod-account procurement.

## 4. Adjustments accepted post-design (A2C4AB.x)

### A2C4AB.1 — `slack_configs` mandatory in `ops-critical`

The preflight discussed Slack on critical as "optional"; user
confirmed it as **mandatory** during brainstorming. PagerDuty pages
the on-call; Slack `#incidents` posts visibility to the rest of the
team simultaneously. Both fire in parallel. Reflected in D2C4AB.2.

### A2C4AB.2 — Five explicit invariants for adapter

User confirmed five additional invariants for the Linear adapter,
captured as I-AB.6 through I-AB.10 in §13:

- Adapter is stateless.
- Adapter has independent lifecycle from runtime-adapters.
- Adapter does NOT persist local state.
- Dedup queries Linear at runtime (no local cache/index).
- Adapter failure does NOT tumbar runtime-adapters.

### A2C4AB.3 — Six explicit clarifications for adapter contract

User requested the spec make the following explicit:

1. Linear has NO native `dedup_key` field; dedup is implemented via
   label metadata.
2. The Alertmanager `groupKey` is the canonical source for the
   dedup hash.
3. The HTML comment in the issue body is debug metadata only,
   NOT the primary matching mechanism.
4. If Linear API is down, the adapter returns 5xx so Alertmanager
   retries.
5. If the event is semantically non-recoverable (e.g., resolved
   before firing), the adapter returns 2xx to avoid retry storms.

All five reflected in §7.

## 5. Design principles

- **D1.1 (CLAUDE.md):** runtime-adapters is the boundary between
  decision and execution. The Linear adapter is **ops infrastructure**,
  not adapter execution — it lives outside the runtime process to
  preserve the boundary.
- **D1.2 (CLAUDE.md):** the repo does NOT decide, route, orchestrate,
  or evaluate policy. The Linear adapter is the documented exception
  to "receivers are configured, not coded" (I-AB.3) — it is necessarily
  a service because Alertmanager has no native Linear receiver.
- **R10 (rules):** config rejected by default. The bootstrap-time
  mode lock (Layer 3) implements this for the CI tenant question:
  if `CI=true` without `RUNTIME_TENANT=test`, abort.
- **R16 (rules):** metric cardinality bounded. The webhook adapter
  is NOT a runtime-adapters component; it has no relation to runtime
  metrics. Its own metrics (request count, Linear API latency) are
  out of scope for `runtime_adapters_*` and live under
  `linear_webhook_adapter_*` if instrumented (deferred — not in
  v0.8.0 closure criteria).
- **Honest tier (D2C4F.8 carry-over):** A+B does NOT promote any
  alert to a confidence tier the bench cannot support. F's calibration
  decisions are unchanged.

## 7. Linear webhook adapter

### 7.3 Dedup contract

```go
// internal/integrations/linear/domain/dedup.go

// DedupLabel computes the deterministic Linear label used to
// identify all issues created by the adapter for a given
// Alertmanager alert grouping. The input is Alertmanager's
// canonical groupKey (a stable identifier per alert grouping —
// see Alertmanager docs §webhook payload).
func DedupLabel(groupKey string) string {
    h := sha256.Sum256([]byte(groupKey))
    return "alert:" + hex.EncodeToString(h[:])[:12]
}
```

Property: `DedupLabel(k1) == DedupLabel(k2)` iff `k1 == k2`. No
collisions in practice (probability ~3.5e-15 for 16^12 namespace).

The adapter applies TWO labels to every issue it creates:

- `alert-managed` (constant, identifies adapter-created issues)
- `alert:<hash>` (per-grouping dedup key)

Lookups use the dedup label as primary key:

```graphql
query FindByDedupLabel($label: String!) {
  issues(filter: { labels: { name: { eq: $label } } }) {
    nodes { id title state { name } }
  }
}
```

### 7.4 Issue schema

**Title format:**

- `severity=critical`: `[CRIT] {alertname} — {capability}` if capability label present, else `[CRIT] {alertname}`
- `severity=warning`: `[WARN] {alertname} — {capability}` (or without capability)

**Labels applied at creation:**

- `alert-managed` (constant)
- `alert:<12-char-hash>` (dedup key, D2C4AB.7)
- `severity:critical` or `severity:warning`
- `capability:<capability>` (only if `capability` label present in alert)

**Priority:** per D2C4AB.10 — critical→P1, warning→P3.

**Body schema (Markdown):**

```markdown
**Alert:** {alertname}
**Severity:** {severity}
**Capability:** {capability if present}
**First fired:** {ISO8601 timestamp}
**Last update:** {ISO8601 timestamp}
**Active alerts in group:** {n}

## Summary
> {commonAnnotations.summary}

## Description
> {commonAnnotations.description}

## Links
- [Alertmanager view]({externalURL})
- [Runbook]({commonAnnotations.runbook}) — if defined
- [Dashboard]({commonAnnotations.dashboard}) — if defined

---

<!-- linear-webhook-adapter dedup metadata. Debug only. Do not edit. -->
<!-- groupKey: {raw groupKey} -->
<!-- dedup_label: alert:<hash> -->
```

The HTML-comment block at the bottom is **debug metadata only** —
NOT the primary matching mechanism. Matching is done via the
`alert:<hash>` LABEL, not by parsing the body comment (A2C4AB.3.3).

### 7.5 Lifecycle

#### 7.5.1 Firing → no existing issue

1. Compute `dedup_label` from `groupKey`.
2. Query Linear: `issues(filter: { labels: { name: { eq: dedup_label } } })`.
3. Result is empty → call `IssueCreate` with full schema.
4. Return 200 OK.

#### 7.5.2 Firing → existing issue

1. Compute `dedup_label`.
2. Query Linear → find most recent issue (latest `createdAt`) in
   non-archived states.
3. Refresh issue body (update `Last update`, `Active alerts in group`).
4. Apply anti-spam logic (D2C4AB.9): add a comment ONLY if alert
   set changed, severity/status flipped, or `LINEAR_RECOMMENT_MIN_INTERVAL`
   elapsed since last comment. Else: just refresh body.
5. Return 200 OK.

#### 7.5.3 Resolved → existing open issue

1. Compute `dedup_label`.
2. Query Linear → find most recent open issue.
3. Add final comment: `Resolved at {ISO8601}, duration {hh:mm:ss}`.
4. Update state to `Cancelled` (per D2C4AB.8 — auto-resolved alerts
   are NOT "Done" semantically; "Cancelled" reads as "the alert
   resolved on its own").
5. Return 200 OK.

#### 7.5.4 Resolved → no existing issue (race condition)

1. Compute `dedup_label`.
2. Query Linear → empty result.
3. Log warning: `received resolved for unknown alert grouping {dedup_label}`.
4. Return **200 OK** (NOT 5xx — semantically non-recoverable, do
   NOT trigger Alertmanager retry; A2C4AB.3.5).

#### 7.5.5 Idempotency under retry

If Alertmanager retries a webhook (because the adapter crashed
mid-create or returned 5xx):

- The dedup query happens BEFORE create — so a second attempt
  finds the issue from the first attempt and updates instead of
  creating a duplicate.
- Idempotency is preserved by **dedup-query-then-write**, not by
  any local state in the adapter.

### 7.6 HTTP semantics

| Scenario | Response |
|---|---|
| Normal firing/resolved processed successfully | 200 OK |
| Alertmanager payload malformed (JSON parse error, missing required fields) | 400 Bad Request — do NOT retry (no amount of retries will fix bad input) |
| Linear API returns 4xx (auth failure, malformed mutation) | 500 Internal Server Error — Alertmanager retries; operator alerted via logs |
| Linear API returns 5xx or times out | 502 Bad Gateway — Alertmanager retries with backoff |
| Resolved without prior firing (race) | 200 OK — log warning, no retry (A2C4AB.3.5) |
| Linear API auth invalid (wrong tenant) | 500 + abort startup if detected at boot (Layer 4) |

### 7.7 Configuration

Env vars consumed by `linear-webhook-adapter` at startup:

```

LINEAR_TEAM_ID                — Linear team ID (test workspace)
LINEAR_API_URL                — defaults to https://api.linear.app/graphql; overridable for tests
LINEAR_DEFAULT_LABEL_IDS      — comma-separated label IDs to apply to every issue (e.g., "alert-managed" label ID resolved at startup)
```

## 8. Smoke target — `make smoke-receivers`

### 8.1 Goal + flow

Demonstrate end-to-end that a real alert lands in all expected
destinations + verify silenced info path. Programmatic verification
per receiver, no human-in-the-loop. Exit 0 on PASS, non-zero on FAIL
(with diagnostics).

```
1. preflight   — env vars present; amtool in PATH; containers up
2. inject      — 3 alerts (critical, warning, info)
3. wait        — sleep 90s (covers critical 30s group_wait + warning 1m group_wait + 30s buffer)
4. verify_pos  — assert critical landed in PD + Slack #incidents; warning landed in Slack #ops + Linear
5. verify_neg  — assert info landed in NONE of the 4 destinations
6. cleanup     — resolve PD incident; chat.delete Slack messages; archive Linear issue; amtool silence test alertnames
7. report      — PASS/FAIL summary; on FAIL dump alertmanager + linear-webhook adapter logs
```

### 8.2 Injection

```bash
amtool --alertmanager.url=http://localhost:9093 alert add \
    alertname=SmokeTestCritical severity=critical adapter=smoke capability=smoke.test@v1 \
    --start="$(date -u +%FT%TZ)" \
    --annotation=summary="Smoke test — verifies routing to PagerDuty + Slack #incidents"

amtool ... alert add alertname=SmokeTestWarning severity=warning ...

amtool ... alert add alertname=SmokeTestInfo severity=info ...
```

### 8.3 Verification per receiver

Per D2C4AB.12. PagerDuty + Linear via API queries straightforward.
Slack requires a bot user with `channels:history` scope on the
test workspace's sandbox channels.

### 8.4 Negative test

Per D2C4AB.13. After the verify_pos step succeeds:

```bash
verify_neg() {
    if pd_query | grep -q "SmokeTestInfo"; then fail "info leaked to PagerDuty"; fi
    if slack_history "#incidents" | grep -q "SmokeTestInfo"; then fail "info leaked to Slack #incidents"; fi
    if slack_history "#ops" | grep -q "SmokeTestInfo"; then fail "info leaked to Slack #ops"; fi
    if linear_issues_by_label "$(dedup_hash SmokeTestInfo)" | grep -q "."; then fail "info leaked to Linear"; fi
}
```

### 8.5 Cleanup

Per D2C4AB.14. Each step is fail-soft (logs warning, continues).

### 8.6 Implementation form

`ops/smoke/smoke-receivers.sh` (Bash, ~250 LOC) wrapped by Make
target. Uses `amtool`, `curl`, `jq`. Same operator-tooling pattern
as `ops/load/lib/`.

## 9. CI guardrails — 4 layers

### 9.1 Layer 1 — Secret scanning (gitleaks)

```yaml
# .github/workflows/ci.yml — new job
secret-scan:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with:
        fetch-depth: 0
    - uses: gitleaks/gitleaks-action@v2
      env:
        GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Runs on every PR + push. Fails CI if any credential pattern matches
the diff. gitleaks ships ~100 patterns out-of-the-box; covers
PagerDuty routing keys, Slack incoming webhook URLs, Linear API
tokens, AWS keys, GitHub PATs.

### 9.2 Layer 2 — Env var name guard

```yaml
# .github/workflows/ci.yml — new job
env-var-guard:
  runs-on: ubuntu-latest
  steps:
    - name: Reject prod credential env vars
      run: |
        leaked=$(env | grep -E '^(PROD_|.*_PROD_|.*_PRODUCTION_)' || true)
        if [ -n "$leaked" ]; then
          echo "FATAL: production credential env vars present in CI environment:"
          echo "$leaked" | sed 's/=.*/=<REDACTED>/'
          exit 1
        fi
```

Convention: production credentials use prefix or infix `PROD_`. Test
tenant vars omit `PROD_`. Documented in `.env.example` and
`docs/test-tenant.md`.

### 9.3 Layer 3 — Bootstrap-time mode lock

In both `internal/bootstrap/wire.go` (runtime-adapters) and
`cmd/linear-webhook-adapter/main.go`:

```go
if os.Getenv("CI") == "true" && os.Getenv("RUNTIME_TENANT") != "test" {
    return fmt.Errorf(
        "FATAL: CI must run with RUNTIME_TENANT=test (got %q)",
        os.Getenv("RUNTIME_TENANT"),
    )
}
```

Tests verify the abort-loud behavior:

- `internal/bootstrap/wire_test.go` — `TestRuntime_AbortsInCIWithoutTestTenant`
- `cmd/linear-webhook-adapter/main_test.go` — analogous

### 9.4 Layer 4 — Per-receiver tenant fingerprinting

Linear adapter (in B2): see §7.8.

Runtime-adapters (in B3): logs `tenant_type` at startup based on
`RUNTIME_TENANT` env var. No PagerDuty/Slack fingerprinting at the
runtime side (runtime does not connect to those — Alertmanager
does).

Smoke target (in B3): explicit fingerprinting checks before
injecting alerts, e.g., asserts `PAGERDUTY_TEST_SERVICE_ID` matches
the expected test service ID stored in `.env.example`-documented
constants.

## 12. Out of scope

The following are explicit non-goals for v0.8.0:

- **Production tenant procurement** (PagerDuty paid plan, Linear
  paid plan, etc.). v0.8.0 ships test-tenant-ready code; prod
  adoption is operational.
- **Multi-region / failover** for the webhook adapter. Single
  instance per environment is sufficient.
- **Custom severity tiers** beyond critical/warning/info.
- **Two-way Slack interaction** (ack alerts from Slack, etc.).
  Bot scope is read-only `channels:history` + `chat:write` for
  cleanup.
- **CI integration** of the smoke target as a gate. Operator-driven
  for v0.8.0; CI integration deferred.
- **Webhook adapter metrics** under `linear_webhook_adapter_*`
  Prometheus namespace. Adapter logs are sufficient for v0.8.0;
  metrics are follow-up if dashboards demand them.
- **Alertmanager HA mode** (multiple Alertmanager instances + gossip).
  Single instance.
- **PagerDuty incident enrichment** beyond the basic Events API v2
  fields. Custom integrations (Datadog-style) are deferred.
- **Linear automation rules** (auto-assign, project routing). Issues
  are created in the configured team with default state; further
  routing is human work in Linear UI.

Any of the above moving into runtime-adapters scope requires an
explicit ADR with default-rejected stance.

## 13. Invariants

These are codified in the spec and NOT subject to renegotiation
during implementation without an ADR:

- **I-AB.1** — `severity: info` NEVER reaches a paging or chat
  receiver. Silenced at the routing tree root via `null-receiver`.
- **I-AB.2** — Production credentials NEVER in CI. Enforced by
  Layers 1+2 (gitleaks + env var name guard) at CI level and
  Layer 3 (bootstrap mode lock) at application level.
- **I-AB.3** — Receivers are configured, not coded, in Alertmanager.
  The Linear webhook adapter is the SINGLE documented exception —
  it is necessarily a service because Alertmanager has no native
  Linear receiver.
- **I-AB.4** — Webhook adapter is **stateless**: behavior on event N
  depends only on event N's payload + Linear API state, not on prior
  events the adapter has seen.
- **I-AB.5** — Test tenant is the development default. PRs that
  hit production credentials by default are rejected at review.
- **I-AB.6** — Webhook adapter has **independent lifecycle** from
  runtime-adapters: separate process, separate restart, separate
  health, separate liveness probes.
- **I-AB.7** — Webhook adapter does NOT persist local state. No
  sqlite, no badger, no file artifacts beyond logs. The container's
  writable layer is treated as ephemeral.
- **I-AB.8** — Dedup queries Linear at runtime via the
  `alert:<hash>` label. No local index, no in-memory cache that
  affects dedup decisions.
- **I-AB.9** — Webhook adapter failure does NOT tumbar
  runtime-adapters. Decoupled by process boundary; no shared
  dependencies critical to runtime startup or operation.
- **I-AB.10** — Smoke target verifies all 3 receivers (positive)
  AND verifies info silenced (negative); no half-measure verification
  (e.g., relying on "trust the protocol" log inspection for any
  single receiver).
