# Phase 2C.3 — Chaos + Minimal Hardening — Design

> **Status:** Design (pre-plan). Produced via `superpowers:brainstorming` on 2026-04-26.
> **Parent:** Phase 2C (Hardening), track 3 of 4 (2C.1 observability ✅ → 2C.2 load baseline ✅ → **2C.3 chaos + minimal hardening** → 2C.4 operational readiness).
> **Predecessor specs:** `docs/superpowers/specs/2026-04-19-runtime-adapters-phase1-design.md`, `docs/superpowers/specs/2026-04-21-phase-2c-observability-slos-design.md`, `docs/superpowers/specs/2026-04-23-phase-2c-load-baseline-design.md`.

## 1. Purpose

Phase 2C.2 closed (`v0.3.0`) with SLO targets calibrated under the pinned compose envelope. Phase 2C.1 already established the observability contract (logger, metrics, Sloth-generated rules, Alertmanager routing, dashboards). The runtime is now measured but **never exercised under deliberate failure**. The operational hypothesis at this point is:

> *Adapters classify correctly under fault; the receipt persists before any caller-visible response (A4.3); metrics reflect the truth; and the observability pipeline fires the correct alert within a derivable budget.*

Phase 2C.3 converts that hypothesis into **evidence** through chaos injection and minimal, evidence-driven hardening.

Three guarantees the track must deliver at close:

1. **Classification fidelity.** Each fault mode in the CI catalogue produces the expected `(status, error_class, retry_hint)` triple in the receipt; the receipt is persisted before the response (A4.3); the corresponding `runtime_adapters_execution_total{status=...}` counter increments.
2. **Pipeline fidelity.** A fault injected against the real binary in a compose environment propagates through the full observability chain — metric scrape → recording rule evaluation → burn rate consumption → Alertmanager fire → receiver stub delivery — with label-precise correctness and a documented timing budget.
3. **Hardening grounded in evidence.** Any gap chaos surfaces (cooperative cancel, child process leak on SIGKILL, panic outside the recoverer, persist race) is closed in its own reactive fix bundle. Zero speculative hardening.

After 2C.3, the runtime moves from "observable" (2C.1) and "calibrated" (2C.2) to **"resilient under known failure modes"**. Operational readiness — runbooks, real receivers, dashboards-with-annotations — remains 2C.4's job.

## 2. Scope

### 2.1 In-scope (2C.3)

- **Chaos decorator framework** — port-level wrappers (`ChaosAdapter`, `ChaosReceiptStore`) implementing `outbound.Adapter` and `ports.ReceiptStore` respectively. Chaos-capable code is compiled into the runtime binary, but is inert by default and fail-closed (§3 principle 1).
- **Bootstrap safety guardrails** — chaos rejected by default; rejected if `RUNTIME_ENV=production`; profile path validated through `filepath.Clean` against an allowlist with no symlink escape and no `..` traversal; profile schema validated against a closed catalogue at startup.
- **CI fault catalogue** — six versioned profile YAMLs in `ops/chaos/profiles/ci/`. Coverage: one fault per adapter (`shell`, `git`, `filesystem`, `http`) + one panic injection + one persist failure. Mapped to a representative diversity of `ErrorClass` values (`Interrupted`, `ExternalFailure`, `AdapterInternalError`).
- **Local-only comprehensive catalogue** — `ops/chaos/profiles/local/*.yaml` (~20-25 profiles) covering realistic fault matrices per adapter. Executable via `make chaos-local PROFILE=<name>`. Never runs in CI per-PR.
- **Toxiproxy integration** — for nightly and local-only network chaos against real upstream endpoints. Toxiproxy never participates in the per-PR canary.
- **Chaos integration tests (per-PR fast)** — six tests, one per CI profile. Each validates classification + receipt persistence + metric increment (per Q6 contract). No Prometheus/Alertmanager. Total runtime under two minutes.
- **Safety-net invariant tests** — three obligatory verifications: panic recoverer mount audit, `ResultNormalizer` determinism (fuzz/property), persistence-before-return invariant under concurrent persist failure.
- **Receiver stub** — standalone Go binary; HTTP listener exposing `POST /alerts`, `GET /inspect[?since=...]`, `DELETE /alerts`; in-memory ring buffer.
- **Compose chaos overlay** — `ops/local/compose.chaos.yaml` extends the 2C.2 base compose. Adds Alertmanager + receiver stub + chaos env wiring + Toxiproxy (profile-gated, nightly/local only). Does not duplicate Prometheus or the OTel collector.
- **Per-PR E2E canary** — single scenario (`http.request@v1` + `connection_reset` injected in-process) executed against the full pipeline; label-precise assertions + tiered timing budget (target 60s, deadline 90s).
- **Nightly comprehensive workflow** — `.github/workflows/chaos-nightly.yaml`; runs all six CI scenarios against the full pipeline plus the inhibition contract assertion. `schedule:` daily + `workflow_dispatch:` manual.
- **N reactive fix bundles** — opened only if chaos surfaces real gaps in B3 (integration tests) or B6 (canary). Tag `v0.4.0` ships at the real close, including reactives.
- **Documentation** — `docs/chaos.md` (operator + dev guide); `docs/adr/0009-chaos-opt-in-compiled-in-code.md`; `docs/adr/0010-receiver-stub-for-am-contract.md`; `docs/adr/0011-two-tier-chaos-ci.md`; new R17 in `docs/rules.md`; new I24 in `docs/domain-invariants.md`.
- **CHANGELOG 0.4.0 + tag `v0.4.0`** at real close.

## 3. Approach

The 2C.3 approach is the hybrid resolution of seven scope-defining questions answered during brainstorming (Q1–Q7, see Appendix A).

Four governing principles:

1. **Chaos-capable code is compiled into the runtime binary, but is inert by default and fail-closed.** Decorators ship with the binary because the e2e canary requires the *real* binary to be the unit under test. They never activate without `RUNTIME_CHAOS_ENABLED=true` AND `RUNTIME_ENV != production`. This is a hard guarantee enforced in bootstrap; partial chaos state is forbidden.
2. **Closed catalogue, validated profile.** Fault keys are a closed enumeration in code; profile YAMLs are validated at startup against the Phase 1 capability catalogue and the fault enum. Unknown keys, malformed paths, or `RUNTIME_ENV=production` cause startup to fail. R17 (§15) formalises this.
3. **Two-tier coverage, derivable timing.** Per-PR CI runs six fast classification tests + one canary E2E with a tiered timing budget derived from documented config (target 60s, deadline 90s). Nightly runs the comprehensive set against the full pipeline plus the inhibition contract. The split keeps PR velocity high while preserving end-to-end signal.
4. **Evidence-driven hardening.** No adapter code changes ship in 2C.3 unless a chaos scenario fails. The seven base bundles cover framework, catalogue, tests, infrastructure, and docs. Reactive fix bundles open only when chaos discovers a real gap. If adapters are sound, the track closes lean.

## 4. Architecture overview

```
                    ┌──────────────────────────────────────────────────┐
                    │ Chaos config (env + profile YAML)                 │
                    │   RUNTIME_CHAOS_ENABLED=true|false  (default false)│
                    │   RUNTIME_CHAOS_PROFILE=<allowlist path>           │
                    │   RUNTIME_ENV=development|staging|production       │
                    └─────────┬─────────────────────────────────────────┘
                              │ read at bootstrap; fail-closed validation
                              ▼
                    ┌────────────────────────────────────────────┐
                    │ chaos.LoadConfig                             │
                    │   reject if RUNTIME_ENV=production           │
                    │   reject if profile path outside allowlist   │
                    │   reject if symlink escape or `..` traversal │
                    │   reject if unknown capability or fault key  │
                    │   on disabled: returns inert config          │
                    └─────────┬──────────────────────────────────┘
                              │ if disabled: maybeWrap is identity
                              │ if enabled:  build decorator chain
                              ▼
   ┌──────────────────────┐                ┌──────────────────────┐
   │ ExecuteService       │ ──── call ───▶ │ ChaosAdapter          │ ── call ─▶ AdapterReal
   │ (application layer)   │                │   implements           │           (shell|git|fs|http)
   └──────────┬───────────┘                │   outbound.Adapter     │
              │                            │   inject pre|post|panic │
              │                            │   → AdapterRawOutcome   │ (R5: still raw)
              │                            └──────────────────────┘
              ▼
   ┌──────────────────────┐
   │ ResultNormalizer     │ ◀── AdapterRawOutcome (chaos or real, indistinguishable shape)
   │ → ExecutionResult    │     (I24: chaos cannot bypass runtime semantics)
   └──────────┬───────────┘
              ▼
   ┌──────────────────────┐
   │ ReceiptBuilder       │
   │ → ExecutionReceipt   │
   └──────────┬───────────┘
              ▼ A4.3 persist before return
   ┌──────────────────────┐                 ┌──────────────────────┐
   │ ChaosReceiptStore    │ ── delegate ──▶ │ ReceiptStore (pg)    │
   │   may inject persist  │                 └──────────────────────┘
   │   failure              │
   └──────────┬───────────┘
              ▼
              return to caller (or 5xx if persist faulted)
```

**Key architectural decisions:**

- **Decorator wraps the adapter, not the service.** `ChaosAdapter` implements `outbound.Adapter` and is injected at registry-build time. R5 holds: the chaos decorator returns `AdapterRawOutcome`, the same shape a real adapter produces; `ResultNormalizer` processes both identically. Receipt building, persistence, metrics, and logging are invariant to chaos presence.
- **Persist chaos lives at the store layer.** `ReceiptStore` is not an `outbound.Adapter`; injecting persist failure inside `ChaosAdapter` would conflate concerns. `ChaosReceiptStore` is a symmetric wrapper around `ports.ReceiptStore`, mounted by the same wiring step.
- **Wiring is linear.** `Application.Wire()` builds real adapters → loads chaos config → calls `maybeWrapAdaptersWithChaos` → continues normal wiring. There is no parallel `WireChaos()` flow. `maybeWrapAdaptersWithChaos` is a pure function and is testable in isolation.
- **Profile maps capability → fault.** A single profile YAML defines what to inject for each capability. Capabilities not listed pass through unchanged. Persist faults live in a top-level `persistence` block.
- **Panic injection lives in `ChaosAdapter`.** A `inject_panic` fault causes the decorator to `panic(...)` before calling the real adapter. R4's panic recoverer must catch it and produce `AdapterInternalError`. This is the central evidence that R4 holds across all real call paths.
- **Compose overlay extends, never duplicates.** Prometheus and the OTel collector come from the 2C.2 base compose; the chaos overlay only adds Alertmanager, the receiver stub, the Toxiproxy service (profile-gated), and chaos env wiring on the runtime container.

## 5. Chaos decorator framework

### 5.1 Decorator port — `ChaosAdapter`

```go
// internal/infrastructure/chaos/chaos_adapter.go

type ChaosAdapter struct {
    real    outbound.Adapter
    profile *Profile           // immutable, loaded at bootstrap
    clock   contracts.Clock
}

func NewChaosAdapter(real outbound.Adapter, profile *Profile, clock contracts.Clock) *ChaosAdapter {
    return &ChaosAdapter{real: real, profile: profile, clock: clock}
}

func (c *ChaosAdapter) Execute(
    ctx context.Context,
    req outbound.AdapterRequest,
) outbound.AdapterRawOutcome {
    fault, ok := c.profile.For(req.Capability())
    if !ok {
        return c.real.Execute(ctx, req)        // pass-through
    }
    return c.dispatchFault(ctx, req, fault)
}
```

`dispatchFault` is a switch over the closed fault enumeration:

```
latency, connection_reset, hang_until_cancel,
eio, enospc, permission_denied,
remote_unreachable, auth_failure,
inject_panic,
process_signal, process_exit,
slow_body, redirect_loop, tls_handshake_fail
```

Every branch produces an `AdapterRawOutcome` of the same shape that the real adapter would produce for the equivalent real fault. This is the architectural commitment behind I24.

`inject_panic` does not return an outcome; it calls `panic(...)` directly, exercising the recovery path established by R4.

### 5.2 Persist chaos — `ChaosReceiptStore`

```go
// internal/infrastructure/chaos/chaos_receipt_store.go

type ChaosReceiptStore struct {
    real    ports.ReceiptStore
    profile *Profile
}

func (c *ChaosReceiptStore) Persist(ctx context.Context, r ExecutionReceipt) error {
    if c.profile.PersistFault() != nil {
        return errChaosPersistFailure
    }
    return c.real.Persist(ctx, r)
}
```

`profile.PersistFault()` returns nil when no persist chaos is configured. When configured, every persist call faults; `ExecuteService` does not return a receipt to the caller; the caller receives a 5xx; `runtime_adapters_receipt_persist_failures_total` increments. A4.3 is exercised end-to-end.

### 5.3 Profile loading + validation

```go
// internal/infrastructure/chaos/profile.go

type Profile struct {
    Version  int
    Name     string
    Adapters map[CapabilityID]FaultConfig    // capability → fault
    Persist  *PersistFaultConfig              // optional
}

func LoadProfile(path string, catalog Catalog) (*Profile, error) {
    cleaned := filepath.Clean(path)
    if !isInAllowlist(cleaned)              { return nil, errPathOutsideAllowlist }
    if hasParentTraversal(cleaned)          { return nil, errParentTraversal }
    if escapesAllowlistViaSymlink(cleaned)  { return nil, errSymlinkEscape }
    // YAML decode, schema-version check, capability and fault validation, etc.
}
```

Allowlist:

- `ops/chaos/profiles/ci/*.yaml`
- `ops/chaos/profiles/local/*.yaml`
- `internal/infrastructure/chaos/testdata/*.yaml`

All three protected paths are checked after `filepath.Clean` and after `os.Readlink` recursion to ensure no symlink in the chain points outside the allowlist.

### 5.4 Wiring path — `Wire()` lineal

```go
func (a *Application) Wire(cfg Config) error {
    // 1. Build real adapters
    realShell, _ := shell.New(cfg.Shell)
    realGit,   _ := git.New(cfg.Git)
    realFS,    _ := filesystem.New(cfg.Filesystem)
    realHTTP,  _ := httpadapter.New(cfg.HTTP)

    // 2. Build registry with reals
    registry := outbound.NewAdapterRegistry()
    registry.Register(shellID, realShell)
    registry.Register(gitStatusID, realGit)
    registry.Register(gitCloneID,  realGit)
    registry.Register(gitDiffID,   realGit)
    registry.Register(gitCommitID, realGit)
    registry.Register(fsReadID,    realFS)
    registry.Register(fsWriteID,   realFS)
    registry.Register(httpRequestID, realHTTP)

    // 3. Build receipt store (real)
    var receiptStore ports.ReceiptStore = pgreceipt.New(cfg.DB)

    // 4. Load chaos config (returns inert config if disabled; error otherwise)
    chaosCfg, err := chaos.LoadConfig(cfg.Chaos, cfg.Env)
    if err != nil {
        return fmt.Errorf("chaos: %w", err)
    }

    // 5. Maybe wrap (no-op if chaosCfg.Enabled == false)
    registry, receiptStore = maybeWrapAdaptersWithChaos(registry, receiptStore, chaosCfg, a.clock)

    // 6. Continue normal wiring
    a.executeService = application.NewExecuteService(registry, receiptStore, /* ... */)
    return nil
}

// Pure function. Fully testable.
func maybeWrapAdaptersWithChaos(
    registry outbound.AdapterRegistry,
    receiptStore ports.ReceiptStore,
    chaosCfg *chaos.Config,
    clock contracts.Clock,
) (outbound.AdapterRegistry, ports.ReceiptStore) {
    if chaosCfg == nil || !chaosCfg.Enabled {
        return registry, receiptStore
    }
    wrapped := outbound.NewAdapterRegistry()
    for _, capID := range registry.Capabilities() {
        real, _ := registry.For(capID)
        wrapped.Register(capID, chaos.NewChaosAdapter(real, chaosCfg.Profile, clock))
    }
    if chaosCfg.Profile.PersistFault() != nil {
        receiptStore = chaos.NewChaosReceiptStore(receiptStore, chaosCfg.Profile)
    }
    return wrapped, receiptStore
}
```

`maybeWrapAdaptersWithChaos` table tests cover: chaos disabled → identity; chaos enabled, no persist fault → registry wrapped, store untouched; chaos enabled, persist fault present → both wrapped.

## 6. CI fault catalogue

### 6.1 Profile YAML schema (v1)

```yaml
version: 1
name: ci-shell-hang-cancel
description: |
  shell.exec@v1 hangs; caller cancels via context deadline.
  Validates Interrupted ErrorClass + non_retryable RetryHint.
adapters:
  shell.exec@v1:
    fault: hang_until_cancel
    timing: post_dispatch
expected_outcome:
  status: cancelled
  error_class: Interrupted
  retry_hint: non_retryable
persistence: null    # no persist chaos in this profile
```

`expected_outcome` is metadata, not enforced by the runtime. Chaos integration tests (§9) read it to assert against the receipt produced by `ExecuteService`. The loader validates that `expected_outcome` is present and well-typed; tests fail loudly if a profile lacks it.

`expected_outcome` is the **stable contract** of the v1 schema (D2C3.24): incompatible changes to the triple `(status, error_class, retry_hint)` require a v2 schema with a documented migration path. Adding new optional top-level fields is permitted as long as v1 tests ignore them.

### 6.2 Six profiles + ErrorClass coverage

| # | Profile name | Capability | Fault | Expected status | Expected ErrorClass | Expected RetryHint |
|---|---|---|---|---|---|---|
| 1 | `ci-shell-hang-cancel` | `shell.exec@v1` | `hang_until_cancel` | `cancelled` | `Interrupted` | `non_retryable` |
| 2 | `ci-git-remote-unreachable` | `git.clone@v1` | `remote_unreachable` | `failure` | `ExternalFailure` | `retryable` |
| 3 | `ci-fs-readfile-eio` | `filesystem.read_file@v1` | `eio` | `failure` | `ExternalFailure` | `retryable` |
| 4 | `ci-http-connection-reset` | `http.request@v1` | `connection_reset` | `failure` | `ExternalFailure` | `retryable` |
| 5 | `ci-shell-panic` | `shell.exec@v1` | `inject_panic` | `failure` | `AdapterInternalError` | `non_retryable` |
| 6 | `ci-persist-fail` | `filesystem.read_file@v1` (success path) | `persistence: { fault: persist_failure }` | (no receipt persisted; caller 5xx; persist_failures counter +1) | n/a | n/a |

Profile #3 (`ci-fs-readfile-eio`) carries an explicit note in its `description`:

> *EIO is treated as external infrastructure I/O failure, not adapter bug. The adapter does not own the disk; a hardware-level read error classifies as ExternalFailure with retryable hint, consistent with how the FS adapter classifies real EIO encountered in production.*

ErrorClass diversity: `Interrupted`, `ExternalFailure` (×3 across distinct adapters), `AdapterInternalError`, plus the persist-failure path. Three distinct classes plus the persistence invariant — sufficient for "razonable mapeo" without forcing 1:1 with the full enum.

Profile #4 (`ci-http-connection-reset`) doubles as the **per-PR canary** scenario (§12).

## 7. Local-only comprehensive catalogue

### 7.1 Matrix

`ops/chaos/profiles/local/*.yaml` — ~20-25 profiles, executed on demand via `make chaos-local PROFILE=<name>`. CI never runs them.

Representative coverage per adapter:

- **shell**: `hang+SIGKILL`, `hang+SIGTERM-ignored`, `segfault` (process_signal), `exit-137`, `stdout-flood`
- **git**: `remote-unreachable`, `auth-failure`, `large-clone-timeout`, `dirty-workdir`, `corrupt-repo`
- **fs**: `eio`, `enospc`, `permission-denied`, `cancel-mid-write`, `slow-disk` (latency)
- **http**: `connection-reset`, `tls-handshake-fail`, `redirect-loop`, `slow-body`, `5xx-storm` (combined latency), `auth-failure`
- **cross-cutting**: `inject-panic` per adapter, `persist-fail`, `pool-exhaustion` (latency on persist), `otel-collector-down` (compose-level toggle, no profile)

Each profile follows the v1 schema (§6.1). `expected_outcome` documents the expected behaviour but is not asserted by an automated test; local profiles are exploratory.

### 7.2 Toxiproxy role

Toxiproxy is **not** required for in-process faults (panic, EIO, hang, persist, process signals). It is required for network-level chaos against **real** upstream endpoints, where the goal is to test how the adapter library reacts to real flap rather than to synthesised raw outcomes:

- `http.request@v1` against a real-but-toxiproxied upstream → real TCP-level latency injection
- `git.clone@v1` against a real-but-toxiproxied SSH/HTTPS endpoint → tests go-git behaviour under degraded transport

Per-PR CI uses in-process injection exclusively (D2C3.2 / A2C3.2). Toxiproxy appears only in the chaos compose overlay under `--profile toxiproxy`, used in nightly runs and local exploration.

## 8. Bootstrap safety guardrails

### 8.1 Env var matrix

| Var | Default | Allowed | Effect |
|---|---|---|---|
| `RUNTIME_CHAOS_ENABLED` | `false` | `true \| false` | If `false`, chaos config is ignored; `maybeWrapAdaptersWithChaos` is identity. |
| `RUNTIME_CHAOS_PROFILE` | `""` | path to `.yaml` inside the allowlist | Required if `ENABLED=true`. |
| `RUNTIME_ENV` | `development` | `development \| staging \| production` | If `production`, chaos is rejected even with `ENABLED=true`. |

Unknown env vars with the `RUNTIME_CHAOS_` prefix produce a startup warning. Other unknown env vars are ignored (R10 applies to the declared config surface; arbitrary env vars are additive by convention).

### 8.2 Fail-closed rules

```go
func LoadConfig(c ChaosConfig, env string) (*Config, error) {
    if !c.Enabled {
        return &Config{Enabled: false}, nil
    }
    if env == "production" {
        return nil, errors.New("chaos: refuses to start with RUNTIME_ENV=production")
    }
    if c.ProfilePath == "" {
        return nil, errors.New("chaos: RUNTIME_CHAOS_PROFILE required when enabled")
    }
    cleaned := filepath.Clean(c.ProfilePath)
    if !isInAllowlist(cleaned) {
        return nil, fmt.Errorf("chaos: profile path %q not in allowlist", cleaned)
    }
    if hasParentTraversal(cleaned) {
        return nil, fmt.Errorf("chaos: profile path %q contains parent traversal", cleaned)
    }
    if escapesAllowlistViaSymlink(cleaned) {
        return nil, fmt.Errorf("chaos: profile path %q escapes allowlist via symlink", cleaned)
    }
    profile, err := LoadProfile(cleaned, ClosedCatalog())
    if err != nil {
        return nil, fmt.Errorf("chaos: profile load failed: %w", err)
    }
    return &Config{Enabled: true, Profile: profile, Env: env}, nil
}
```

The loader rejects:

- Profile schema version != 1
- Capability not in Phase 1 catalogue
- Fault type not in closed enum
- Path outside allowlist
- Path containing `..` after `filepath.Clean`
- Path with a symlink resolving outside the allowlist
- `RUNTIME_ENV=production` (regardless of `ENABLED` flag)

Every rejection causes `Application.Wire()` to return error; main aborts; no partial chaos state is ever observable.

### 9.2 Per-test contract (Q6 = c)

For each subtest, in order:

1. **Build app with chaos enabled** (test fixture sets `RUNTIME_CHAOS_ENABLED=true`, `RUNTIME_CHAOS_PROFILE=<testdata path>`, `RUNTIME_ENV=development`).
2. **Execute the targeted capability** via the in-process SDK peer.
3. **Receipt classification.** Assert `receipt.Status`, `receipt.ErrorClass`, `receipt.RetryHint` match `expected_outcome` from the profile.
4. **Receipt persisted.** Query `SELECT 1 FROM execution_receipts WHERE id = $1`. For the persist-fail case, assert the negative — no receipt persisted, and the caller received an error.
5. **Metric incremented.** Snapshot the OTel in-memory `manual.Reader`. Assert `runtime_adapters.execution.total{capability=<capID>, status=<status>}` incremented by 1, or `runtime_adapters.receipt.persist.failures` incremented by 1 in the persist-fail case.

No log-level assertions, no Prometheus, no Alertmanager, no compose. Total runtime target: ~30s for all six subtests.

CI gate: any failure blocks PR merge.

## 10. Safety-net invariant tests

### 10.1 Panic recoverer mount audit

`internal/integration/chaos/panic_audit_test.go`. Verifies R4 across every call path where a panic could plausibly occur.

```go
cases := []struct {
    name     string
    invoke   func(*Application) error
    location PanicLocation
}{
    {"adapter-execute",       invokeWithAdapterPanic,     LocationAdapterExecute},
    {"normalizer-fault",      invokeWithNormalizerPanic,  LocationNormalizer},     // synthetic
    {"persist-fault",         invokeWithPersistPanic,     LocationPersist},
    {"idempotency-replay",    invokeWithReplayPanic,      LocationIdempotencyReplay},
}
```

For each case:

- Caller receives 5xx; no hang.
- Receipt produced with `status=failure, error_class=AdapterInternalError, retry_hint=non_retryable`.
- **Log emitted at level ERROR** with `error_class=adapter_internal_error` and a new field `panic_location=<location>`. (`panic_location` is a log-only additive field, not a receipt field — D2C3.16.)
- Metric `runtime_adapters.adapter.panics{adapter=<adapter>}` incremented (where applicable to the location).

This is the only test in 2C.3 that asserts log-level contract. Q6 = c does not require log-level checks per scenario; this audit fulfils that contract once and authoritatively.

### 10.3 Persistence-before-return invariant

`internal/integration/chaos/persist_invariant_test.go`. An explicit and stricter variant of `ci-persist-fail`.

- Inject persist failure.
- Run 100 concurrent execution requests against the same capability.
- Assert: zero receipts found in DB.
- Assert: zero callers received a successful response.
- Assert: every caller received a 5xx response.
- Assert: `runtime_adapters_receipt_persist_failures_total` counter == 100.
- Assert: no caller saw a `200 OK` while the DB query returned empty for that receipt ID (closes the A4.3 race window).

## 11. Receiver stub + compose chaos overlay

### 11.1 Receiver stub

`ops/chaos/receiver/main.go` — standalone Go binary, ~80-120 LOC.

Endpoints:

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/alerts` | Alertmanager webhook target. Stores received alerts in an in-memory ring buffer (cap 1000). Returns 200 OK. |
| `GET` | `/inspect` | Returns `{"received": [...]}` — the full buffer as JSON. Used by tests for polling. |
| `GET` | `/inspect?since=<rfc3339>` | Filtered view: alerts received at or after the timestamp. |
| `DELETE` | `/alerts` | Clears the buffer. Used between test cases. |

In-memory only; no persistence; no auth (lives entirely on a local docker network). Ships as a `scratch`-based image from `ops/chaos/receiver/Dockerfile`.

### 11.2 Compose overlay

`ops/local/compose.chaos.yaml` extends `ops/local/compose.yaml` (the 2C.2 envelope-pinned base). Adds **only** what the chaos pipeline needs:

## 12. Per-PR E2E canary

### 12.1 Test architecture

`internal/integration/chaos/canary_e2e_test.go` — build tag `e2e`. Triggered by GHA job `chaos-canary-e2e`. Requires a docker daemon on the runner (already available in compose-based jobs from 2C.2).

Flow:

```
1. SETUP
   1a. Render Sloth specs with TEST overrides:
       sloth generate --default-slo-period 5m \
         --input ops/slo/ \
         --output ops/local/test-slo-rules.yaml
   1b. docker compose \
         -f ops/local/compose.yaml \
         -f ops/local/compose.chaos.yaml up -d
       (env: RUNTIME_CHAOS_ENABLED=true,
             RUNTIME_CHAOS_PROFILE=/etc/chaos/ci-http-connection-reset.yaml,
             AM_GROUP_WAIT=5s,
             RUNTIME_ENV=development)
   1c. wait_for_healthy on runtime, prometheus, alertmanager, receiver-stub.

2. EXERCISE
   T0 = now()
   for i := 0; i < 30; i++ {
       POST /api/v1/executions  // payload: http.request@v1 → localhost:9099 (chaos intercepts)
       sleep 500ms              // ~15s of sustained failure
   }

3. ASSERT
   poll receiver-stub /inspect every 1s until budget exhausted OR matching alert found
   matching alert =
       alertname  = "HttpRequestAvailabilityBurn"
     AND capability = "http.request@v1"
     AND adapter    = "http"
     AND severity   = "critical"
     AND sloth_slo  = <expected, read from rendered rules>
   on match:
       record fire_latency = now() - T0
       if fire_latency > 60s: log warning (budget overshoot but within deadline)
       if fire_latency > 90s: fail

4. CLEANUP
   docker compose down -v
```

### 12.2 Timing budget — derivation and tiering

The budget is derived from documented config, not chosen arbitrarily.

```
T_scrape_interval     =  1s   (compose.chaos prometheus override)
T_evaluation_interval =  1s   (compose.chaos prometheus override)
T_sloth_window_min    = ~5s   (Sloth --default-slo-period 5m + fast-burn evaluation)
T_alert_for           =  5s   (Sloth-rendered)
T_am_group_wait       =  5s   (compose.chaos AM override)
T_am_routing          = ~2s   (delivery to receiver-stub on docker network)
T_margin_ci           = ~40s  (CI runner jitter, container scheduling, scrape staggering)
─────────────────────────────
T_target              = 60s   (canary objective)
T_deadline            = 90s   (operational ceiling; 30s additional margin)
```

**Tiered behaviour** (D2C3.21):

- `fire_latency ≤ 60s` → test passes silently.
- `60s < fire_latency ≤ 90s` → test passes but emits a warning (logged + included in test output) so trend can be tracked.
- `fire_latency > 90s` → test fails.

The derivation table is replicated verbatim in `docs/chaos.md` and updated whenever the budget changes. Raising the budget is a deliberate commit with a justification block in the message.

### 12.3 Label assertion contract

```go
type ExpectedAlert struct {

```

### 13.2 Per-scenario contract (extended)

Each of the six CI scenarios runs against the full pipeline (not just classification):

- Same SETUP/EXERCISE/ASSERT cycle as the canary (§12.1) but parameterised by the profile under test.
- Label-precise assertions + tiered timing budget (60s target / 90s deadline).
- **Plus inhibition contract** — for scenarios that fire a critical alert, assert that no warning alert with the same `(sloth_slo, capability)` is delivered during the test window.
- Persistence and metric assertions still applied (subsume Q6 = c assertions).

Total expected wall time: ~6 × 90s exercise + shared setup/teardown = ~15-20 min.

### 13.3 Inhibition contract test

```go
// After the critical alert is observed, also assert no warning with same SLO+capability.
warnings := stub.AlertsMatching(ExpectedAlert{
    Severity:   "warning",
    SLOName:    expected.SLOName,
    Capability: expected.Capability,
})
require.Empty(t, warnings,
    "inhibition violated: warning alert delivered for same SLO+capability as critical")
```

This validates D2C1.17 (Alertmanager inhibition uses `sloth_slo` + `capability`). Without inhibition active, both critical and warning would fire; with inhibition, only critical reaches the receiver.

### 13.4 Failure handling

Nightly failure flow (D2C3.22):

1. **Artifact dump** preserved as a GHA artifact (90 days retention). Includes Prometheus query snapshots, Alertmanager state, receiver-stub `/inspect` JSON, and runtime container logs.
2. **Auto-issue creation** via `gh issue create` directly (no third-party action). Body includes:
   - The failing scenario name.
   - Stage breadcrumbs from the test diagnostics.
   - A link to the GHA workflow run and the artifact bundle.
   - Label `chaos-nightly-fail`.
3. **Robustness:** if the issue creation step itself fails (rate limit, token issue), the artifact dump still runs and the workflow ends in failure with a clear log line. No information loss.
4. PRs are not blocked. Triage is human and same-day or next-day.
5. If a scenario fails three nights consecutively, a human decides whether to open a reactive fix bundle, raise the budget with justification, or mark the scenario as `known-flaky` with an explicit tracked issue.

## 15. New rules and invariants

### 15.1 R17 — Chaos disabled by default and fail-closed in production

Added to `docs/rules.md`:

> **R17 — Chaos disabled by default and fail-closed in production.** Chaos-capable code is compiled into the runtime binary but is inert unless `RUNTIME_CHAOS_ENABLED=true` AND `RUNTIME_ENV != production`. Profile loading enforces:
>
> 1. Profile path passed through `filepath.Clean`; absolute paths only inside the allowlist (`ops/chaos/profiles/**` or `internal/infrastructure/chaos/testdata/**`).
> 2. No symlink resolution that escapes the allowlist (`os.Readlink` checked recursively).
> 3. No `..` traversal in path components.
> 4. Profile schema version enforced (v1 only).
> 5. Every capability key in the profile must be in Phase 1's closed catalogue.
> 6. Every fault type in the profile must be in the closed enum (§5.1).
> 7. No dynamic profile loading at runtime; no remote sources.
>
> Any rule violation, or `RUNTIME_ENV=production` with chaos enabled, causes startup failure. `Application.Wire()` returns error; main aborts. Partial chaos state is forbidden.

### 15.2 I24 — Chaos injection must not bypass runtime semantics

Added to `docs/domain-invariants.md`:

> **I24 — Chaos injection must not bypass runtime semantics.** A fault produced by chaos injection must result in an `ExecutionReceipt` that is shape-identical, classification-identical, and lifecycle-identical to a real fault of the same kind. The same rules apply: `ResultNormalizer` is invoked unchanged; receipt is built unchanged; persistence-before-return (A4.3) holds; metrics emit unchanged; logs emit at the level dictated by `LevelFor(status, error_class)`. A test or operator inspecting a receipt cannot tell whether the fault was real or injected — by design.

R17 governs the operational surface (when chaos may run, how it is loaded). I24 governs the semantic surface (what chaos may and may not change about runtime behaviour). Together they define the contract that lets chaos validate the runtime rather than mock it.

## 16. Out of scope (explicit recap)

To preserve focus, the following items are explicitly excluded from 2C.3:

- Recovery / resolved alert assertion + delivery latency p95 — **2C.4**.
- Real receiver integrations (PagerDuty, Opsgenie, Linear, Slack) — **2C.4**.
- Strong sandboxing (gVisor, Firecracker, nsjail, container-per-execution) — **post-2C**.
- `LockManager` / `ResourceClaims` design — **post-2C**, except as a reactive fix if chaos exposes a concrete race.
- Chaos against production traffic — **never in this repo** (R1).
- `tc netem` or kernel-level network primitives — **rejected** (Toxiproxy covers network chaos).
- Build-tag chaos binary — **rejected** (Q2 chose decorator opt-in).
- Kubernetes chaos primitives — **post-2C**.
- Auto-remediation / self-healing — **never** in runtime-adapters (R1).
- Deliberate degradation SLOs separate from current SLOs — **2C.4 if needed**.
- Chaos-derived recalibration of SLO targets — **rejected** (calibration belongs to 2C.2).
- Multi-tenant chaos isolation — **post-multi-tenancy**.
- Saga compensations triggered by chaos — **post-orchestrator**.
- Chaos automation (failure budgets, automatic rollback) — **belongs to `agent-governance-core`**.
- Loki integration for chaos-test logs / alert correlation — **2C.4 if demanded**.
- Annotation overlay on dashboards for chaos test runs — **2C.4 if demanded**.

## 17. Schema versioning and breaking changes

- **Profile schema v1**: locked for 2C.3. The stable contract within v1 is `expected_outcome.{status, error_class, retry_hint}` — incompatible changes require a v2 schema with a documented migration path. Adding new optional top-level fields is permitted as long as v1 tests ignore them.
- **Fault enum**: additions are additive (no ADR). Removals require ADR and a one-release deprecation window.
- **Receiver stub `/inspect` JSON shape**: stable contract; renaming or removing fields requires ADR (tests and the nightly workflow depend on it).
- **R17 fail-closed semantics**: changes require ADR + spec update.
- **`compose.chaos.yaml` env var contract** (`RUNTIME_CHAOS_*`): stable; renames require ADR.
- **I24 semantics**: a chaos-induced receipt being distinguishable from a real-fault receipt is itself a breaking change of the runtime contract; would require ADR + invariant update.
