# Phase 2C.4 / G — Cancellation-rate + persist-availability SLOs

> **Parent:** Phase 2C (hardening), track 4 of 4 (operational readiness),
> sub-project G of A-H (per `docs/phase-2c.4-roadmap.md`).
> **Closes at tag:** `v0.5.0`.
> **Status:** ACCEPTED 2026-04-29.
> **Authors / approvers:** Russell + assistant (brainstorming session
> 2026-04-29).

## 1. Summary

Sub-project G adds two SLO families to close gaps surfaced during 2C.3:

1. **Cancellation rate (per Phase 1 capability)** — 8 SLOs measuring
   `cancelled / total` execution rate per canonical capability. Re-enables
   the `ci-shell-hang-cancel` chaos scenario in `TestChaos_Comprehensive`.
2. **Persist availability (global)** — 1 SLO measuring receipt persistence
   reliability. Re-enables the `ci-persist-fail` chaos scenario.

No runtime Go code changes. No new metrics, no new labels, no metric
contract change. Pure SLO YAML additions + a single defensive Go contract
test that protects the SLI denominator derivation. Sloth renders the
burn-rate recording rules + alerts the same way it does for existing
SLOs.

The two chaos scenarios that ship skipped in `v0.4.0`
(`ci-shell-hang-cancel`, `ci-persist-fail`) become active again under
their respective new alerts, and the nightly comprehensive suite returns
to 6/6 active scenarios.

## 2. Goals / non-goals

### Goals

- **G1.** Define `cancellation-rate` SLO for each of the 8 Phase 1
  canonical capabilities. Per-capability granularity for operational
  drill-down.
- **G2.** Define `persist-availability` SLO globally (no capability
  label). Runtime-wide receipt-persistence reliability signal.
- **G3.** Provide test variants of all 9 SLOs under `ops/slo/test/` so
  the chaos comprehensive suite can exercise them under short-window
  burn-rate.
- **G4.** Re-enable both currently-skipped chaos scenarios
  (`ci-shell-hang-cancel`, `ci-persist-fail`) in
  `test/chaos/e2e/comprehensive_test.go`. Nightly chaos returns to 6/6.
- **G5.** Add a contract test
  (`Test_RecordExecution_OnlyAfterPersistSuccess`) that defends the SLI
  denominator derivation against future refactors of `execute_service.go`.
- **G6.** Ship `v0.5.0` with CHANGELOG entry.

### Non-goals

- **NG1.** Real-load calibration of the new objectives. Initial values
  ship PROVISIONAL with documented rationale; recalibration with
  evidence is a follow-up if production signal demands.
- **NG2.** Routing the new alerts to real pager/ticket receivers. That's
  sub-project A+B (`v0.8.0`).
- **NG3.** Aggregated cancellation-rate SLO (single global). Decided
  per-capability only — see D2C4G.4.
- **NG4.** Adding a `capability` label to the persist counter. Would be
  a metric-contract change; decided global-only — see D2C4G.5.
- **NG5.** Re-enabling the three chaos scenarios skipped at 2C.3 design
  time (stdout-flood, dirty-workdir, corrupt-repo). Different problem
  (no closed-catalogue fault representation). Future reactive bundle if
  demanded.
- **NG6.** Adding a new `runtime_adapters.receipt.persist.attempts`
  counter. Decided to derive denominator from existing metrics — see
  D2C4G.1.
- **NG7.** Cancellation-rate or persist-availability rules for SLOs
  outside the Phase 1 canonical set. Catalogue is frozen.

## 3. Design principles

- **P1 — Zero runtime Go code changes (other than the contract test).**
  G ships YAML + Sloth render + one `_test.go` file. The metric contract
  (R3) stays frozen; the rule and alert contracts (R3) stay frozen.
- **P2 — Match the existing SLO pattern.** Cancellation SLOs follow the
  same shape as availability+latency SLOs (per-capability, Sloth burn-rate
  alerting, page+ticket severity). Operators reading
  `ops/slo/shell.yaml` already understand the structure; G adds 1 SLO
  per capability under the same contract.
- **P3 — Derive, don't add.** Persist-availability denominator is
  derived from existing metrics
  (`execution.total + receipt.persist.failures`), exact-not-approximate
  per the `RecordExecution`-after-persist invariant established post-B8/B9.
  Adding a new counter would be redundant.
- **P4 — Protect the derivation with a contract test.** Because the
  denominator's correctness is load-bearing on a code-ordering invariant
  (`RecordExecution` only after persist success), a defensive Go test
  asserts that ordering directly. If a future refactor breaks it, the
  test fails loudly with a message pointing at the SLI it protects.
- **P5 — Inhibition rule unchanged.** The existing
  `equal: ['sloth_slo', 'capability']` clause in
  `ops/alertmanager/alertmanager.yaml` already handles both labeled and
  unlabeled SLOs (Alertmanager treats absent-label-on-both-source-and-target
  as equal). No alertmanager changes needed.
- **P6 — PROVISIONAL targets.** Initial objectives are operator
  hypotheses (cancellation 99.0%, persist 99.9%). Calibration is
  out-of-scope per roadmap §G; YAML headers carry an explicit PROVISIONAL
  marker matching 2C.1 convention.

## 4. SLO definitions

### 4.1 Cancellation-rate SLO (per capability)

**Phase 1 canonical capabilities** (8): `shell.exec@v1`,
`git.status@v1`, `git.clone@v1`, `git.diff@v1`, `git.commit@v1`,
`filesystem.read_file@v1`, `filesystem.write_file@v1`, `http.request@v1`.

**Per-SLO shape (template):**

```yaml
- name: "<adapter>-<cap>-cancellation-rate"
  objective: 99.0   # PROVISIONAL — cancellation rate < 1% (G, 2C.4)
  description: "<cap>@v1 caller-cancellation rate (PROVISIONAL — see file header)"
  labels:
    capability: "<cap>@v1"
  sli:
    events:
      error_query: |
        sum(rate(runtime_adapters_execution_total{capability="<cap>@v1",status="cancelled"}[{{.window}}]))
      total_query: |
        sum(rate(runtime_adapters_execution_total{capability="<cap>@v1"}[{{.window}}]))
  alerting:
    name: <Cap>CancellationRateBurn
    labels:
      capability: "<cap>@v1"
    page_alert:
      labels:
        severity: critical
    ticket_alert:
      labels:
        severity: warning
```

**SLI semantics.** Numerator = cancelled executions. Denominator = ALL
executions (all 5 statuses: success | failure | timeout | cancelled |
partial). Cancellation rate at 100% (chaos profile) gives error_ratio =
1.0; burn-rate alerts trip fast against the 99.0% objective (1% budget).

**Alert names** follow PascalCase capability convention:
`ShellExecCancellationRateBurn`, `GitCloneCancellationRateBurn`,
`GitStatusCancellationRateBurn`, `GitDiffCancellationRateBurn`,
`GitCommitCancellationRateBurn`,
`FilesystemReadFileCancellationRateBurn`,
`FilesystemWriteFileCancellationRateBurn`,
`HttpRequestCancellationRateBurn`.

**File layout.** SLOs land **inside the existing per-adapter SLO files**
(`ops/slo/{shell,git,filesystem,http}.yaml`). Each adapter gains 1
cancellation-rate SLO per capability it owns:

| File | New SLO entries |
|---|---:|
| `ops/slo/shell.yaml` | 1 (shell-exec-cancellation-rate) |
| `ops/slo/git.yaml` | 4 (status, clone, diff, commit) |
| `ops/slo/filesystem.yaml` | 2 (read_file, write_file) |
| `ops/slo/http.yaml` | 1 (request) |
| **Total** | **8** |

Rationale: keeps "all SLOs of an adapter in one place" — extension of
the existing pattern.

### 4.2 Persist-availability SLO (global)

**New file:** `ops/slo/persist.yaml`. Standalone because the SLO is not
adapter-specific.

```yaml
service: "runtime-adapters"
labels:
  team: "platform"

slos:
  - name: "persist-availability"
    objective: 99.9   # PROVISIONAL — persist failure rate < 0.1% (G, 2C.4)
    description: "Receipt persistence reliability across all capabilities (denominator derived per comment in total_query)"
    sli:
      events:
        error_query: |
          sum(rate(runtime_adapters_receipt_persist_failures[{{.window}}]))
        # Denominator derivation (D2C4G.1):
        #   total_persist_attempts =
        #     successful_persists  (every execution.total fires AFTER a
        #                           successful persist per
        #                           execute_service.go RecordExecution
        #                           semantics post-B8/B9)
        #   + failed_persists       (receipt.persist.failures counter)
        #
        # Mathematically EXACT, not approximate. Protected by
        # Test_RecordExecution_OnlyAfterPersistSuccess in
        # internal/application/services/execute_service_test.go (§7 of this spec).
        # If that test ever fails, this denominator is wrong — fix the
        # ordering in execute_service before touching this SLI.
        total_query: |
          (
            sum(rate(runtime_adapters_execution_total[{{.window}}]))
            +
            sum(rate(runtime_adapters_receipt_persist_failures[{{.window}}]))
          )
    alerting:
      name: PersistAvailabilityBurn
      page_alert:
        labels:
          severity: critical
      ticket_alert:
        labels:
          severity: warning
```

**SLI semantics.** Numerator = persist failures. Denominator = total
persist attempts, derived exactly via P3. Persist failure rate at 100%
(chaos profile) gives error_ratio = 1.0; burn-rate trips fast against
99.9% objective.

**Prom metric name verified:** dashboard at
`ops/grafana/dashboards/runtime-overview.json:493` uses
`runtime_adapters_receipt_persist_failures` (no `_total` suffix); SLI
selectors must match this exact name.

**No `capability` label.** D2C4G.5 — the metric is `labels: nil` per
`internal/infrastructure/obs/metrics.go:49`. Adding capability would be
a metric-contract change (R3), out of scope. The inhibition rule
(`equal: ['sloth_slo', 'capability']`) treats absent capability on both
source and target as equal — no alertmanager change required.

## 5. Test SLO variants

Mirror the chaos B6 pattern. Each new SLO gets a corresponding test SLO
spec under `ops/slo/test/` with `service: "runtime-adapters-chaos-test"`
to avoid `sloth_slo` label collision with prod when both are loaded in
the same Prometheus instance.

| Test file | New entries |
|---|---:|
| `ops/slo/test/shell.yaml` | +1 (shell-exec-cancellation-rate) |
| `ops/slo/test/git.yaml` | +4 |
| `ops/slo/test/filesystem.yaml` | +2 |
| `ops/slo/test/http.yaml` | +1 |
| `ops/slo/test/persist.yaml` | NEW (persist-availability) |

**Render command** (existing `make chaos-render-rules`):

```bash
sloth generate \
  --input=ops/slo/test \
  --out=ops/prometheus/generated/test \
  --default-slo-period=5m \
  --slo-period-windows-path=ops/slo/windows
```

Output lands in `ops/prometheus/generated/test/{shell,git,filesystem,http,persist}.yaml`
— one file per spec, glob-ed by `ops/prometheus/prometheus.chaos.yml`'s
`rule_files: [/etc/prometheus/test-rules/*.yaml]`.

**SLO period 5m** (test) vs **30d** (prod) — same convention as B6's
test-only rule rendering. Short-window burn-rate alerts trip within the
canary's 90s deadline budget.

### 6.3 Inhibition assertion for global SLO

`comprehensive_test.go::runComprehensiveScenario` calls
`rc.AlertsMatchingSince(ctx, exp, criticalAlert.Received)` with
`exp.Capability = ""` for the persist-fail scenario.

Verified compatible without helper changes:
`test/chaos/e2e/receiver_client.go::alertMatches` (line 202-216)
already implements match-by-omission — every `exp.<Field> != ""` check
is gated, so `exp.Capability == ""` skips the capability check entirely
and the matcher accepts payloads regardless of the `capability` label
value or absence. The same pattern applies to `exp.AlertName`,
`exp.SLOName`, `exp.Severity`. No receiver-client change needed.

**Inhibition semantics for the global persist SLO:** Sloth emits both
the critical (page-tier) and warning (ticket-tier) alerts under a
single `alertname: PersistAvailabilityBurn`, differentiated by
`severity`. Both alerts carry `sloth_slo: persist-availability`; neither
carries `capability`. Alertmanager's inhibition rule
(`equal: ['sloth_slo', 'capability']`) treats both alerts as equal on
the capability dimension because the label is absent on both source
and target — inhibition is active for the global SLO without changes.

## 7. Defensive contract test (Go)

**Type:** Contract test for SLI metric semantics — protects the
denominator derivation in `ops/slo/persist.yaml` against future
refactors of `execute_service.go` that would silently invalidate the
SLO math. **NOT** a regular unit test. Must be marked clearly in the
test file as "contract test" with an inline comment that points at the
SLO it defends.

**Location:**
`internal/application/services/execute_service_test.go`.

**Name:** `Test_RecordExecution_OnlyAfterPersistSuccess`.

**Header comment (mandatory shape):**

```go
// Test_RecordExecution_OnlyAfterPersistSuccess is a CONTRACT TEST for the
// metric semantics that ops/slo/persist.yaml depends on.
//
// The persist-availability SLI derives its denominator as:
//   total_persist_attempts =
//     execution.total{any status} (= successful persists)
//     + receipt.persist.failures  (= failed persists)
//
// This is exact ONLY IF execution.total is incremented strictly AFTER
// a successful persist. If a future refactor reorders execute_service
// to emit RecordExecution before or in parallel with persist, the
// denominator goes wrong silently and the SLO produces meaningless
// ratios.
//
// This test forces both branches:
//   (1) persist succeeds  → execution.total += 1, persist.failures += 0
//   (2) persist fails     → execution.total += 0, persist.failures += 1
//
// If either assertion fails, the SLI in ops/slo/persist.yaml is no
// longer valid — fix the ordering in execute_service.go BEFORE
// touching the SLI.
//
// See spec: docs/superpowers/specs/2026-04-29-phase-2c.4-g-cancellation-persist-slos-design.md §7
```

**Test mechanics.**

- Use the `manual.Reader` pattern already in
  `internal/infrastructure/obs/exemplar_test.go` (build a meter provider
  with a manual reader, register the runtime metric Registry against it,
  exercise execute_service, snapshot the reader).
- Use the existing `ChaosReceiptStore` (`internal/infrastructure/chaos`)
  to inject persist failure deterministically. Assert on the snapshot.
- The test is `_test.go`-only. No production code changes.
- Tag: regular unit test (no `integration` or `e2e` tag), runs in the
  `lint + unit + contract` GHA job.

**Failure-mode behavior.** If the assertion fails, the test message
must include:
- The actual counter values seen.
- A pointer at the SLO file: "ops/slo/persist.yaml total_query is no
  longer valid — see spec G §7."
- A pointer at the spec section.

This pattern is the project's first contract test for metric semantics;
it sets the precedent for future SLOs that derive from existing metrics
rather than introducing new ones (P3).

## 8. PROVISIONAL header convention

Each new SLO YAML file gets a header block at the top, matching 2C.1's
PROVISIONAL convention:

```yaml
# PROVISIONAL — initial operational hypothesis (Phase 2C.4 sub-project G).
# Cancellation/persist objectives are NOT yet calibrated against real-load
# data. Recalibrate with evidence under the load envelope (ADR 0008,
# docs/load-baseline.md) when production traffic gives signal.
# Tracked: 2C.4 sub-project G; closes at v0.5.0.
```

Existing per-adapter files (`ops/slo/shell.yaml`, `git.yaml`,
`filesystem.yaml`, `http.yaml`) already have a "Calibrated 2C.2" header.
The G additions are slotted into the same files but introduce
PROVISIONAL objectives. Resolve via:

- Each NEW cancellation SLO entry carries `objective: 99.0   # PROVISIONAL` as an
  end-of-line comment.
- Each NEW SLO entry's `description:` field includes "(PROVISIONAL — see
  file header)".
- The file's top-of-file header gets a SECOND block underneath the
  existing 2C.2 calibrated block:
  ```yaml
  # ---
  # 2C.4 / G additions: cancellation-rate SLOs are PROVISIONAL.
  # Cancellation objectives (99.0%) are operator hypotheses, not
  # calibrated. Recalibrate with evidence per docs/load-baseline.md.
  ```

`ops/slo/persist.yaml` is new and gets only the PROVISIONAL block.

## 10. Closed decisions

Numbered as `D2C4G.<n>`.

- **D2C4G.1** — Persist-availability SLI denominator derived from
  existing metrics (`execution.total + receipt.persist.failures`),
  exact via `RecordExecution`-after-persist invariant. NO new
  `persist.attempts` counter. Brainstormed 2026-04-29 (option β).
- **D2C4G.2** — Cancellation-rate SLO is per-Phase-1-capability (8
  SLOs). NOT aggregated. Reasoning: drill-down operationality;
  matches existing per-capability availability+latency pattern;
  inhibition rule already keys on capability. Brainstormed
  2026-04-29 (option p).
- **D2C4G.3** — Persist-availability SLO is global (1 SLO, no
  capability label). Reasoning: persist counter is `labels: nil`;
  adding capability would be a metric-contract change (R3 / R16);
  the failure mode being measured is runtime-wide regardless of
  which capability triggered it.
- **D2C4G.4** — Initial PROVISIONAL objectives: cancellation 99.0%,
  persist 99.9%. Reasoning: cancellation is caller-correlated and
  semantically less severe than failure (1% rate is operator-tolerable);
  persist is runtime-critical (R7) and 99.9% is the industry baseline
  for storage operations. Both subject to recalibration with evidence.
- **D2C4G.5** — File layout: cancellation SLOs in existing per-adapter
  files; persist SLO in new `ops/slo/persist.yaml`. Reasoning: keeps
  capability-related SLOs co-located per existing pattern; persist is
  not adapter-specific so deserves its own file.
- **D2C4G.6** — `Test_RecordExecution_OnlyAfterPersistSuccess` is a
  contract test for SLI semantics, not a unit test. The header comment
  must explicitly call this out; failure messages must point at the SLO
  spec it protects. Per user adjustment 2026-04-29.
- **D2C4G.7** — Inhibition rule unchanged. Existing
  `equal: ['sloth_slo', 'capability']` covers both labeled and unlabeled
  SLOs (Alertmanager treats absent-on-both as equal). No alertmanager
  change required. Sub-project A+B revisits routing; G does not touch it.
- **D2C4G.8** — `ci-persist-fail` re-enable drives traffic via
  `http.request@v1` (simplest payload to construct; persist fault is
  cross-cutting on any execution path; choice does not affect alert
  fire). The `canonicalCap` field stays empty (global SLO).
