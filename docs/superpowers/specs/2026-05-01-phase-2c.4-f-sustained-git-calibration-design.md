## 1. Summary

Sub-project F closes the calibration deuda from 2C.2: three git capabilities
(`git.clone@v1`, `git.diff@v1`, `git.commit@v1`) currently ship with
`PROVISIONAL / ROUGH_NO_CHANGE` latency targets in `ops/slo/git.yaml`,
and `git.status@v1` is `SMOKE_CALIBRATED` with limited confidence. F runs
the full 2C.2 load baseline pipeline once with two scenario-file changes
(thresholds + iteration bumps) so the existing `generate-report.sh`
emits filtered sub-metrics for the git tier. Post-evidence, the
operator updates `ops/slo/git.yaml` with new `le` values from existing
histogram buckets, writes a new calibration report under
`ops/slo/calibration-reports/`, and ships `v0.7.0`.

No runtime Go code changes. No new metrics. No new labels (R16
unchanged). Histogram buckets unchanged (R3 metric contract frozen).
The cancellation-rate SLOs added in G stay untouched — they're a
different SLO family.

### 1.1 Post-implementation correction (2026-05-02 — B1.5)

The first B2 baseline run on 2026-05-02 surfaced a wiring miss in
the original §4 design: the spec instructed B1 to modify
`ops/load/scenarios/git_rough.js` and `ops/load/scenarios/git_status.js`,
but `make load-baseline` runs `ops/load/scenarios/suite.js` (a separate
self-contained entrypoint with its own `options.scenarios` and
`thresholds:` blocks). k6 only honors `options` from the entrypoint
file; per-scenario `options` from imported files are NOT inherited.
Result of the first run: bumped iterations did not take effect
(clone ran 20 iter / 5m, commit ran 10 iter / 4m), observation-only
thresholds did not surface, and the per-tree split + rough-tier
sections of the report shipped with `null` data (only the
git.status aggregate landed correctly because it comes from the
existing core-tier extraction path).

**Fix (B1.5, bundled into B2 PR per operator decision):**

- All B1 changes also applied to `ops/load/scenarios/suite.js`:
  `git_clone_rough.iterations` 20→60, `maxDuration` 5m→15m;
  `git_commit_rough.iterations` 10→30, `maxDuration` 4m→6m;
  `T_GIT_ROUGH_*` start-time constants recomputed (diff 43m45s→53m45s,
  commit 45m→55m); 6 observation-only thresholds for clone/diff/commit;
  2 per-tree thresholds for git.status (`tree:small-repo`, `tree:dirty-tree`).
- `gitCommit()` in suite.js was a stub (left over from Bundle 3 of
  the original 2C.2 plan) that called `executeRequest` against a
  non-existent workdir — replaced with the same
  clone → filesystem.write_file → git.commit chain that
  `git_rough.js`'s `commitScenario` performs, so suite.js now produces
  real git.commit measurements rather than instant-failure iterations.

**Lesson learned (binding for future load-test work in this repo):**

Any change to k6 `options` that must affect the baseline run MUST
be applied to `suite.js` (the baseline entrypoint), not only to
per-capability scenario files. The per-cap files (`git_rough.js`,
`git_status.js`, `shell_exec.js`, etc.) are entrypoints only when
run directly (e.g., `k6 run /scripts/git_rough.js`); they are
NOT mounted into suite.js's runtime options. The original design's
single-source-of-truth assumption was wrong. Future calibration
changes should either (a) edit suite.js as the canonical source
and let per-cap files be ad-hoc smoke runners, or (b) apply edits
to BOTH files with a comment cross-referencing the duplication.

**Total wall-time impact of B1.5:** suite end time pushes from
~45m to ~61m + ~2m generate-report = ~63m total. The failed
partial v1 (timestamped 2026-05-02) was deleted before the
re-run; `generate-report.sh`'s version counter increments only
against existing files, so the corrected run reuses the `v1`
slot and produces a fresh `2026-05-02-baseline-v1.md`. The
original `2026-04-25-baseline-v2.md` (2C.2 historical baseline)
is preserved untouched.

## 2. Goals / non-goals

- **G1.** Add observation-only k6 thresholds to `git_rough.js` so the
  generate-report pipeline emits filtered sub-metrics (p50/p95/p99) for

  the per-tree split is k6-side evidence used to decide the SINGLE
  capability-keyed SLO target.
- **G3.** Bump iteration counts for low-sample scenarios:
  `git.clone` 20 → 60, `git.commit` 10 → 30. `git.diff` unchanged
  (already ~300 samples). Without these bumps, p99 cannot reach
  `CALIBRATED` confidence (high) and would stay at `SMOKE_CALIBRATED`

- **G4.** Operator runs `make load-baseline` (one-time, ~50 min wall)

  `ops/slo/calibration-reports/2026-05-01-git-sustained.md` (mirroring

- **G5.** Update `ops/slo/git.yaml` with new `le` values **derived

  Values must come from the existing bucket set
  `{0.1, 0.25, 0.5, 1, 2, 3, 5, 10, 30, 60}` per the 2C.2 calibration
  heuristic (smallest bucket ≥ 3× measured p99, with documented
  headroom).
- **G6.** Ship `v0.7.0` with CHANGELOG entry summarising the calibration
  outcomes per capability and any cross-validation drift detected on
  the four core caps (shell/fs/http) re-run during the same baseline.

## 3. Design principles

- **P1 — Match the 2C.2 calibration playbook.** Same envelope (2 CPU /
  2 GiB runtime per ADR 0008). Same load harness. Same heuristic
  (smallest bucket ≥ 3× p99). Same report format. F is a
  re-application of the 2C.2 methodology to the git tier, not a new
  approach.
- **P2 — Observation-only / instrumentation thresholds.** The k6
  thresholds added to `git_rough.js` and `git_status.js` are
  **instrumentation**, not SLO targets. Their primary function is to
  force k6 to emit filtered sub-metrics — without thresholds, k6's
  `handleSummary` does not include the per-tag p50/p95/p99 breakdown
  the report needs. Loose values (10× expected p99) make these
  thresholds essentially never fail under normal conditions; they
  exist to instrument, not to gate. **They CAN fail if performance
  catastrophically regresses** (e.g., diff p99 jumps from sub-100ms
  to >10s), and that is intentional — the run would surface a
  pre-existing regression rather than silently produce a calibration
  baseline against degraded behavior.
- **P3 — Evidence-first YAML changes (no pre-assumption).** New `le`
  values for the git capabilities are derived from the report's
  observed p99, not from this spec. The implementation plan separates
  scenario changes (B1) from YAML updates (B2 or later) so reviewers
  can see the report evidence before approving target deltas.
- **P4 — Bucket reuse (R3 unchanged).** Every new `le` must come from
  `{0.1, 0.25, 0.5, 1, 2, 3, 5, 10, 30, 60}`. If the measured p99
  doesn't fit cleanly with 3-5× headroom, the decision is to round to
  the next-higher bucket OR document `SMOKE_CALIBRATED` / `ROUGH_NO_CHANGE`
  if the tier doesn't fit — never propose a new bucket.
- **P5 — R16 unchanged.** The runtime metric label set
  (`capability`, `adapter`, `status`, `signal`) is not extended. Per-
  tree analysis lives only in the k6 summary JSON evidence file.
- **P6 — Honest confidence tiers.** Per the 2C.2 baseline-v2 pattern:
  - `CALIBRATED` (high) — N ≥ 100 samples, p99 stable, headroom ≥ 3×.
  - `SMOKE_CALIBRATED` (limited) — N 30-100, OR p99 unstable.
  - `ROUGH_NO_CHANGE` — N < 30 OR variance too high; keep PROVISIONAL.
  Do NOT mark a capability `CALIBRATED` if the evidence doesn't
  support it. Honest demotion to SMOKE/ROUGH is preferred over false
  high-confidence claims.

#### 4.1.b Add observation-only thresholds

Currently `git_rough.js` declares:

```js
// NO thresholds — rough tier does not gate on anything.
summaryTrendStats: ['min', 'avg', 'p(50)', 'p(95)', 'p(99)', 'max', 'count'],
```

Replace the `// NO thresholds` comment + add a `thresholds:` block:

```js
// Observation-only / instrumentation thresholds (Phase 2C.4 / F).
//
// These thresholds are NOT SLO targets — their primary function is to
// force k6 to emit filtered sub-metrics in handleSummary keyed by the
// `capability` and `tier` tags. Without a threshold reference, k6's
// summary does NOT include per-tag p50/p95/p99 breakdowns, which means
// the calibration-report generator cannot extract per-capability
// observed values (lesson from
// ops/slo/calibration-reports/2026-04-25-baseline-v2.md:155).
//
// Values are deliberately ~10× expected p99 — high enough to NEVER
// fail under normal conditions. They CAN fail if performance
// catastrophically regresses (e.g., diff p99 from sub-100ms to >10s),
// and that is intentional: the run would surface a pre-existing
// regression rather than silently produce a calibration baseline
// against degraded behavior.
thresholds: {
    'http_req_duration{capability:git.clone@v1,tier:rough}':  ['p(99)<60000'],
    'http_req_failed{capability:git.clone@v1,tier:rough}':    ['rate<1'],
    'http_req_duration{capability:git.diff@v1,tier:rough}':   ['p(99)<10000'],
    'http_req_failed{capability:git.diff@v1,tier:rough}':     ['rate<1'],
    'http_req_duration{capability:git.commit@v1,tier:rough}': ['p(99)<10000'],
    'http_req_failed{capability:git.commit@v1,tier:rough}':   ['rate<1'],
},
summaryTrendStats: ['min', 'avg', 'p(50)', 'p(95)', 'p(99)', 'max', 'count'],
```

The `rate<1` failure thresholds are a guard against 100% failure — only
trips if every request fails, which would invalidate any p99 claim
anyway.

### 4.2 `ops/load/scenarios/git_status.js`

The file already has aggregate thresholds for the smoke phase. F adds
two per-tree thresholds.

Currently:

```js
thresholds: {
    'http_req_duration{phase:smoke,capability:git.status@v1}': ['p(99)<2000'],
    'http_req_failed{phase:smoke,capability:git.status@v1}':    ['rate<0.01'],
},
```

After:

```js
thresholds: {
    // Existing aggregate thresholds (unchanged).
    'http_req_duration{phase:smoke,capability:git.status@v1}': ['p(99)<2000'],
    'http_req_failed{phase:smoke,capability:git.status@v1}':    ['rate<0.01'],
    // F (2C.4) per-tree instrumentation thresholds. NOT SLO targets —
    // their function is to force k6 to emit filtered sub-metrics tagged
    // by `tree=small-repo|dirty-tree` so the calibration report can
    // analyze whether dirty trees are materially slower than clean
    // ones. The runtime SLO for git.status@v1 stays a SINGLE
    // capability-keyed SLO (no `tree` label on the runtime metric —
    // R16 unchanged); the per-tree split informs the threshold decision
    // but does not surface as a label.
    //
    // Loose values (~25× current SMOKE_CALIBRATED p99 of ~50ms) — these
    // CAN fail if a tree-shape regression appears, deliberately
    // surfacing degradation rather than calibrating against it.
    'http_req_duration{capability:git.status@v1,tree:small-repo}': ['p(99)<5000'],
    'http_req_duration{capability:git.status@v1,tree:dirty-tree}': ['p(99)<5000'],
},
```

The `tree` tag is already emitted by `git_status.js` per the 2C.2
50/50 alternation logic — see the file header comment block referencing
`exec.scenario.iterationInTest % 2`. This change ONLY adds the
threshold reference so k6 produces the filtered sub-metrics.

## 5. Run methodology

Operator-driven, locally. Same as 2C.2. ~50 min wall clock.

```bash
# 1. Regenerate fixtures (deterministic, ~5s)
make fixture-git-bench

# 2. Full baseline run (~50 min — bumped from ~45 by clone/commit
#    iteration increases)
make load-baseline
```

`load-baseline` does:

1. Build runtime image (`docker build -t runtime-adapters:ci-test .`).
2. Bring up 7-service pinned compose, wait for health.
3. Run `verify-limits.sh` to confirm cgroup envelope (NanoCpus + Memory
   + MemoryReservation match expected; aborts on drift).
4. Run k6 against `suite.js`. With the bumped iterations, total wall
   is now ~50 min. The git tier dominates the latter half.
5. Generate report at `ops/slo/calibration-reports/<auto-date>-git-sustained.md`
   (the date comes from the run; for this spec we expect 2026-05-01
   or similar). Evidence files land under
   `ops/slo/calibration-reports/evidence/<date>-git-sustained/`.
6. Update `ops/slo/calibration-reports/latest-baseline.json` with the
   new run's per-capability p50/p95/p99 snapshots.

If the run fails (e.g., a threshold trips because of catastrophic
regression — see P2), STOP. Do NOT update `git.yaml` from a failed run.
Investigate the regression first.

## 6. Calibration heuristic (2C.2 carbon copy)

Per capability:

1. Compute observed p99 from the report.
2. Find the smallest bucket in `{0.1, 0.25, 0.5, 1, 2, 3, 5, 10, 30, 60}`
   such that `bucket >= 3 × p99`.
3. Document headroom = `bucket / p99` (factor).
4. Decision tier (per P6):
   - `CALIBRATED` (high confidence) — N samples ≥ 100, p99 stable
     across the run window, headroom ≥ 3×.
   - `SMOKE_CALIBRATED` (limited confidence) — N samples 30-100,
     OR p99 unstable across the window.
   - `ROUGH_NO_CHANGE` — N samples < 30 OR variance too high;
     keep PROVISIONAL.
5. **Per-tree decision (git.status only):** if `dirty-tree p99 >
   1.5 × small-repo p99`, use the dirty-tree p99 as the basis for the
   SINGLE SLO threshold. If they're comparable, use the aggregated p99.
   The report documents the split explicitly with both numbers and the
   chosen basis.

This heuristic mirrors 2C.2 baseline-v2 exactly. F does not invent
methodology.

## 7. SLO YAML update strategy (post-evidence only)

**Critical:** new `le` values are NOT defined in this spec. They come
from the operator's report. The implementation plan separates the
scenario-modification step from the YAML-update step so reviewers can
see the evidence before approving target deltas.

For each capability whose decision is `CALIBRATED`:

- Update the `le=<bucket>` value in the latency `bucket` selector at
  `ops/slo/git.yaml`.
- Update the `description:` field — drop "PROVISIONAL" / "ROUGH" /
  "high variance" markers; add "Calibrated — Phase 2C.4 / F sustained
  baseline".
- The `objective:` (e.g., 99.0) stays unchanged unless evidence shows
  the objective is unreachable (which would be a separate decision
  beyond F's scope).

For each capability staying `SMOKE_CALIBRATED` or `ROUGH_NO_CHANGE`:

- Keep the current `le` value.
- Update the description to cite the F report as the latest evidence
  and the reason the tier didn't advance (e.g., "N=37 samples, headroom
  2.1× — not enough for high-confidence CALIBRATED; F (2C.4) recorded
  evidence at <report path>").

Update the file header at top of `git.yaml`:

- Drop the "Mixed calibration state — Phase 2C.2" block.
- Add a "Calibrated — Phase 2C.4 / F sustained baseline 2026-05-01"
  block describing the new per-capability state.

The G additions block (`# 2C.4 / G additions: git-*-cancellation-rate
SLO(s) are PROVISIONAL`) at lines 13-18 stays untouched — F doesn't
calibrate cancellation rates.
