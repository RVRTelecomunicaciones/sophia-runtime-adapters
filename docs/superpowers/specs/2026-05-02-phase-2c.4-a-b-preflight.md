## 2. Closed decisions

### 2.1 Pager provider — PagerDuty (Events API v2)

`PagerDuty Events API v2` is the integration target.

- Stateless POST with `routing_key` + `dedup_key` + `severity` +
  `summary` + payload.
- Native Alertmanager support via `pagerduty_configs:` (no custom
  adapter needed — see §4 for the case where a custom adapter IS
  needed, which is Linear).
- PagerDuty test service WITHOUT real on-call assignment is
  mandatory for development (see §6).

**Why not Opsgenie:** equivalent integration, but PagerDuty has
materially better community/docs and dominates the ecosystem. No
existing client contract with Opsgenie that would change this.

### 2.2 Warning channels — Slack + Linear (split)

Warnings route to **both** Slack and Linear, by design:

- **Slack** — real-time visibility; humans see the warning fire
  immediately on a chat surface they already monitor.
- **Linear** — persistent tracking; warnings that survive a chat
  scroll-buffer become issues with a lifecycle (open → triaged →
  closed) and an owner.

The two are NOT redundant — they serve different operational needs.
A warning that is only in Slack will be lost in scrollback. A warning
that is only in Linear will not surface fast enough. Both is correct.

### 2.3 Info severity — null / silenced (invariant)

`severity: info` is **silenced at Alertmanager** and routes to NO
receiver. Codified as an invariant in `alertmanager.yml`:

> Any future alert with `severity: info` MUST NOT reach any paging
> or chat receiver. If informational signal is needed, it goes to
> metrics + dashboards, never to alerts.

This is binding — see §7.

### 2.4 Secret store — tiered

Secret credentials (PagerDuty `routing_key`, Slack webhook URL,
Linear API token) live in different stores per environment:

| Environment | Store | Notes |
|---|---|---|
| Local dev | `.env` excluded via `.gitignore` + direnv | Per-developer; never committed |
| CI | GitHub Secrets | Only loaded for **smoke** jobs (see §2.6); never for unit/integration |
| Production | Vault / AWS Secrets Manager / 1Password Connect | Decided per target deploy environment — see §3.2 |

The exact prod store stays open until §3.2 resolves.

### 2.5 Test tenant — mandatory

A+B development MUST NOT use the production tenant of any provider:

- **PagerDuty:** create a test service WITHOUT on-call assignment.
  Free tier supports up to 5 services; this fits comfortably.
- **Slack:** dedicated sandbox channel (`#alerts-test` or equivalent
  in a sandbox workspace).
- **Linear:** dedicated test workspace OR test project labeled `test`
  within the production workspace.

See §6 for the full test tenant policy.

### 2.6 CI secret policy — no production secrets in CI

CI **never** loads production credentials.

- Unit + integration tests use **mock receivers** — no network calls
  to PagerDuty / Slack / Linear.
- Smoke jobs (if any in CI) load **test-tenant** credentials only
  via GitHub Secrets, scoped to the smoke job, not the whole pipeline.
- Local smoke (`make smoke-receivers` or equivalent — TBD in spec)
  uses developer's `.env` test-tenant credentials.

Codified as an invariant — see §7.

## 3. Open questions (resolve before brainstorming finishes)

### 3.1 Provider accounts — are they provisioned?

- **PagerDuty:** does the client (RVR Telecomunicaciones) have an
  active account? Free tier suffices for test service; production
  use requires a paid tier (typically $21/user/month).
- **Linear:** does the client have an active workspace? Free tier
  supports up to 10 users + 1 team — suffices for tracking
  internal alerts.
- **Slack:** confirmed available (the test sandbox channel can be
  created in any existing workspace).

**If accounts are NOT provisioned yet:** A+B targets the **test
tenant only** for `v0.8.0`, and a follow-up bundle ships the
production wiring once accounts are provisioned. We do NOT block
A+B on account procurement.

**If accounts ARE provisioned:** `v0.8.0` ships test + production
wiring together.

### 3.2 Target deploy environment — drives prod secret store choice

The choice between Vault, AWS Secrets Manager, and 1Password Connect
depends on where `runtime-adapters` runs in production:

| Environment | Prod secret store |
|---|---|
| Self-hosted Kubernetes | Vault (or k8s sealed-secrets if simpler) |
| AWS-native | AWS Secrets Manager |
| Hybrid / multi-cloud | 1Password Connect |
| Not yet decided | Default to environment-variable-with-runtime-validation; revisit when prod target lands |

Resolve this question during brainstorming. It does NOT block the
abstract design — the secret-loading interface in Go can stay store-
agnostic via a small config surface.

## 4. Scope disclosure — Linear webhook adapter (B-something)

**Alertmanager has NO native receiver for Linear.** Native receivers
exist for PagerDuty, Slack, OpsGenie, VictorOps, Webhook, Email — but
NOT Linear.

To route warnings to Linear, A+B MUST include a small webhook adapter
service that:

1. Receives Alertmanager webhook POSTs (Alertmanager's standard
   webhook receiver shape).
2. Translates the payload to Linear's GraphQL API (create issue OR
   update existing issue if `dedup_key` matches).
3. Returns 2xx on success, 4xx/5xx on failure (Alertmanager retries
   on 5xx).

### 4.1 Estimated size and shape

- ~300 lines of Go (excluding tests).
- Lives at `internal/integrations/linear-webhook/` or as a separate
  binary at `cmd/linear-webhook-adapter/` — decide during brainstorming.
- Hexagonal: input port (HTTP) → application service → output port
  (Linear API client) — same architectural shape as the rest of the repo.
- Configurable via env vars: `LINEAR_API_TOKEN`, `LINEAR_TEAM_ID`,
  `LINEAR_DEFAULT_LABEL_IDS`, `LISTEN_ADDR`.
- Deployed alongside `runtime-adapters` (same compose / k8s manifest)
  so secrets handling stays uniform.

### 4.2 Why webhook adapter, not Slack-mediated or email-mediated

We considered three options:

| Option | Why rejected |
|---|---|
| Slack-bot mediator (Slack workflow → Linear) | Opaque chain of external dependencies; failure modes are non-debuggable from our side |
| Linear via email (Linear inbox-email creates issues) | Cannot set assignee/priority/labels via email; cannot dedup with `dedup_key`; not enough control |
| **Webhook adapter (chosen)** | We control the translation; testable; deduppable; deploy-uniform with the rest of the repo |

### 4.3 Testing

- Unit: HTTP handler tests + Linear API mock.
- Integration: testcontainers + a local mock Linear endpoint.
- Smoke: drive a real warning through the adapter against the test
  tenant Linear workspace; assert the issue gets created with
  expected fields.

### 4.4 Deduplication contract

The adapter MUST treat Alertmanager's `groupKey` (or a deterministic
hash of the alert labels) as the Linear issue dedup key. Repeated
`firing` events for the same alert update the existing issue's body
+ comment count; `resolved` events close the issue (or move to a
`resolved` state — decide in brainstorming).

This is the "B" of A+B in spirit: A is the receivers wiring; B is
the Linear adapter that makes warning-tracking actually work.

## 5. Routing baseline matrix

The Alertmanager routing tree starts from this matrix:

| Severity | PagerDuty | Slack channel | Linear |
|---|---|---|---|
| `critical` | ✅ — page on-call | ✅ — `#incidents` | ❌ — page is enough |
| `warning` | ❌ — not page-worthy | ✅ — `#ops` | ✅ — open issue |
| `info` | ❌ | ❌ | ❌ — silenced |

The matrix is NOT exhaustive — it is the baseline. If a specific
alert has nuanced routing (e.g., a critical that should ALSO open a
Linear issue for post-incident review), the spec adds explicit
routing nodes for it. But the **default** for each severity is the
table above.

## 6. Test tenant policy

Hard rules for development:

1. **PagerDuty:** test service named `runtime-adapters-test` or
   similar, configured with NO on-call schedule. Pages from this
   service appear in the PagerDuty UI but NEVER wake up a human.
   Document the service ID in the spec.
2. **Slack:** dedicated sandbox channel (`#alerts-test` is the
   default name, but operator may choose). Members of this channel
   should be A+B implementers + reviewers, NOT the broader engineering
   team. Document the channel name in the spec.
3. **Linear:** dedicated test workspace OR a project labeled `test`
   within the prod workspace, with NO assignees. Issues created here
   are for test purposes and may be deleted en masse.
4. **Smoke flow:** the local smoke target (`make smoke-receivers` or
   similar — name decided in spec) drives a real alert end-to-end
   against the test tenant. CI may run this against test tenant via
   GitHub Secrets if the operator wants — but it is acceptable to
   leave smoke as a local-only operator workflow (same pattern as
   `make load-baseline`).

A+B's "real smoke" exit criterion is: an operator can run
`make smoke-receivers` locally and observe the alert land in (a)
PagerDuty test service, (b) Slack sandbox channel, and (c) a new
Linear test issue. Until that works end-to-end, A+B is not done.

## 7. Invariants

These are codified in the spec and NOT subject to renegotiation
during implementation without an explicit ADR:

- **I-AB.1 — `severity: info` NEVER reaches a receiver.** Any future
  alert with `severity: info` is silenced at Alertmanager. Adding an
  info-routed receiver requires an ADR with default-rejected stance.
- **I-AB.2 — Production credentials NEVER in CI.** CI may load
  test-tenant credentials via GitHub Secrets for smoke jobs; CI may
  NOT load production credentials under any circumstance. Verified
  by a CI guardrail check in the pipeline.
- **I-AB.3 — Receivers are configured, not coded.** PagerDuty + Slack
  routing lives in `monitoring/alertmanager/alertmanager.yml`.
  Adding a new severity routing requires editing the config, NOT
  shipping new Go code. (The Linear adapter is the single
  exception — it is a service, not a config change, because
  Alertmanager has no native Linear receiver.)
- **I-AB.4 — Webhook adapter is stateless.** The Linear adapter does
  NOT persist state. Dedup happens via Linear API queries by
  dedup_key (labels hash). Restarting the adapter mid-incident
  MUST NOT change behavior.
- **I-AB.5 — Test tenant is the dev default.** Any PR opened against
  A+B that hits production credentials by default (instead of test
  tenant) is rejected at review.
